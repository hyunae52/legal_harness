# 조회 전용 A: 기존 GCE 전환·복구 실행안

이 파일은 실행 승인이 아니다. Linux/설치/재시작 증거를 확보한 후보를 별도 Pro 배포 검수와 마지막 사람 일괄 검수에 제출하기 위한 운영자 절차다. B의 DB migration·접수·자기수정 worker·무인 갱신 활성화는 포함하지 않는다. 이전 계획 A3의 DNS 전제는 아래 실측에 따라 수정한다.

## 확인된 현재 상태와 수정 범위

1. 기존 root-owned systemd 앱은 main `d41e4588ecd374eedf5a7a846942ce27a17bf7f5`, 공개 `*:3000`에 구동 중이다. `allow-taxlab-mcp` ingress rule이 `0.0.0.0/0 tcp:3000`을 허용한다. 이 구형 HTTP 앱은 rollback 대상이 아니다.
2. cta cron에는 10분마다 main을 pull/build/restart하는 `cron-git-sync.sh`와 매일 upstream을 갱신하는 `update-korean-law.sh`가 있다. **머지 전에 두 작업을 동결**한다. 자동 갱신은 B의 후보 생성·검수 경로를 완성할 때까지 재활성화하지 않는다.
3. Cloudflare zone은 PENDING이다. 가비아 UI와 `.kr` 상위 권한 서버에서 `ns.gabia.co.kr`, `ns1.gabia.co.kr`, `ns.gabia.net`, `kai.ns.cloudflare.com`, `laila.ns.cloudflare.com`의 혼합 delegation을 직접 확인했다. `law` CNAME은 이미 proxied이므로 프록시를 켜는 것으로 해결되지 않는다.
4. 가비아 소유자 로그인 확인. 네임서버 변경에는 휴대전화 또는 이메일 소유자 인증이 필요하다. 마지막 승인 후 해당 절차를 진행한다. DNSSEC UI 데이터 없음, `.kr` DS 조회도 DS 없음. DNSSEC 해제를 지시하지 않는다.
5. 가비아 권한 DNS와 Cloudflare의 기존 레코드를 대조했다. `taxlab.kr`, `dev.taxlab.kr`, `www.taxlab.kr` A는 모두 `54.116.105.82`. root SPF/Google verification, dev SPF, `_dmarc` TXT도 일치하며 MX 없음. 전환 직전에 전체 레코드를 다시 읽고 추가/차이가 있으면 HOLD한다. 기존 세 A를 Cloudflare **DNS only**로 준비하여 현재 direct-origin 동작을 유지하고, `law`만 proxied로 둔다. 이는 승인 묶음에 포함되는 설정 변경이다.

## 마지막 사람 검수에 제시할 묶음

Draft PR #3의 현재 base B, head H, tree T, 정확한 H의 CI run/attempt/event/checkout/필수 step 성공, artifact hash, stage manifest, 아래 실행·복구 명령, 별도 Pro의 실제 배포 준비 판정이다. Pro 응답은 사람이 승인한 것으로 해석하지 않는다. H 또는 B/T, artifact/설정이 바뀌면 같은 승인으로 실행하지 않는다. PR #1/#2는 따로 머지하지 않는다.

CI `pull_request` event의 provider head/merge SHA와 명시적으로 checkout한 H를 구분한다. provider API의 job/step 결론이 전부 실제 `success`이며 skip/누락이 없어야 한다. CI log의 package SHA와 위 artifact가 같아야 한다. 운영 VM에서 TypeScript build를 수행하지 않는다. 320 MiB V8 heap 제한으로 실제 빌드가 실패했던 이력이 있어 신뢰된 Linux build artifact를 설치했다.

## 승인 후 실행 순서

### 1. 정확한 후보 및 복구 경로 재확인

기존 검증된 SSH로 접속한다. 아래 명령은 GCE의 cta 세션에서 실행한다. 비밀값을 stdout에 출력하지 않는다.

```sh
node /home/cta/verify-a-candidate.mjs /home/cta/a-staged-manifest.json edc4ce73ddd0623a0aed77921c70d6bde8b12e2d985c386dcf9d2941a94f8fd6
systemctl is-active legal-harness-a.service legal-harness-maintenance.service cloudflared.service
curl --fail --silent http://127.0.0.1:3100/health
curl --silent --output /dev/null --write-out '%{http_code}\n' http://127.0.0.1:3101/health
sudo cloudflared --config /home/cta/cloudflared-a.yml tunnel ingress validate
sudo cloudflared --config /home/cta/cloudflared-maintenance-a.yml tunnel ingress validate
```

maintenance는 정확히 503이어야 한다. candidate health는 위 버전·규칙 및 `maintenance:unavailable`, active=0이어야 한다. 이전 안전 HTTPS release는 없으므로 복구는 준비한 503이다. 별도 SSH 접속을 유지한다.

### 2. 구형 자동 작업 동결 → 승인한 묶음만 merge

```sh
python3 /home/cta/freeze-legacy-cron.py
python3 /home/cta/freeze-legacy-cron.py --apply
```

이 helper는 두 cron 줄만 주석 처리하고 mode 600 원본을 `/home/cta/.legal-harness-operator-backups`에 보존한다. 이미 실행된 updater가 있거나 두 줄이 달라지면 merge 전에 HOLD한다. cron 교체 후 process 목록에서 두 updater가 모두 종료된 상태인지 다시 확인한다. 동결 이후 실패해도 구형 자동 작업을 자동 복원하지 않는다.

GitHub에서 PR #3을 사용자가 검수한 B/H로 **merge commit 방식**으로 병합한다. 실제 M을 fetch하여 부모가 `[B,H]`이고 `M^{tree}=T`인지 검증한다. squash/rebase·예상하지 못한 부모/tree는 HOLD. `main`이 이동했으면 기존 승인을 사용하지 않는다. tree가 같은 artifact를 그대로 사용하고 재빌드하지 않는다. 실제 CI/Pro/사용자 승인 기록과 M을 함께 저장한다.

### 3. 먼저 안전한 유지보수 경계 확보

DNS activation은 수분 이상 걸릴 수 있다. DNS 정리 전에 구형 앱이 새 도메인으로 노출되지 않도록 **maintenance origin으로 먼저 전환**한다. 이 구간부터 기존 HTTP 이용자는 접속할 수 없으며 DNS 전파 중에는 503조차 보이지 않을 수 있다. 첫 전환을 무중단이라고 약속하지 않는다.

```sh
sudo install -o root -g root -m 0600 /etc/cloudflared/config.yml /root/legal-harness-cloudflared-before-a.yml
sudo install -o root -g root -m 0600 /home/cta/cloudflared-maintenance-a.yml /etc/cloudflared/config.yml
sudo systemctl restart cloudflared.service
sudo systemctl enable legal-harness-maintenance.service
sudo systemctl disable --now legal_harness.service
```

GCE 동일 프로젝트의 VPC 방화벽 **`allow-taxlab-mcp`를 비활성화**한다. SSH 22 및 다른 기존 규칙은 바꾸지 않는다. 로컬 `ss`에서 3000 listener 없음, 별도 Windows 네트워크에서 `136.67.179.84:3000` TCP 연결 실패를 관찰한다. VM에 IPv6가 새로 추가됐으면 그것도 검사한다. 구형 프로세스/자식 종료를 확인한다.

### 4. 전체 도메인 DNS를 보존하며 정상화

Cloudflare에서 위 세 기존 A의 DNS only 및 TXT parity를 확인한 다음, 가비아에서 네임서버를 **`kai.ns.cloudflare.com`, `laila.ns.cloudflare.com` 두 개로만** 지정한다. 가비아 3개는 제외한다. 소유자 인증은 사용자와 진행한다. 도메인 소유권/연장/잠금/인증서 검증 정책은 변경하지 않는다.

`.kr` parent delegation, Cloudflare zone ACTIVE 및 edge 인증서 활성, 서로 다른 recursive resolver 2개, 외부 TLS hostname 검증을 확인한다. `law`는 준비한 maintenance 503이어야 한다. 기존 root/www/dev의 DNS와 HTTPS 상태도 사전값과 대조한다(root HEAD 405/Allow GET, dev HTTPS 401/Basic DevOnly는 기존 응답). 다른 호스트 장애가 생기면 후보 공개 전환은 HOLD하고 DNS 레코드 parity부터 복구한다. 혼합 NS나 공개 HTTP로 되돌리지 않는다.

DNS 준비 단계는 15분 candidate 검증 창과 구분한다. 전파 대기는 실제 상태를 확인하며 사용자에게 알리고, 관찰되지 않은 HTTPS/503을 통과로 쓰지 않는다. DNS/TLS가 준비되지 않으면 `public_port_closed/service_unavailable/recovery_unverified`로 남기고 후보를 공개하지 않는다.

### 5. DNS 준비 후 후보 전환 및 15분 검증 창

1단계 identity를 다시 대조한다. 바로 다음 명령 시점부터 15분을 측정한다.

```sh
sudo install -o root -g root -m 0600 /home/cta/cloudflared-a.yml /etc/cloudflared/config.yml
sudo systemctl restart cloudflared.service
sudo systemctl enable legal-harness-a.service
```

외부 Windows의 검증된 bridge 설치로 HTTPS doctor, 실제 MCP tools/list와 `search_law(query=소득세법,display=1)`를 확인한다. TLS/redirect 검증을 완화하지 않고 키는 환경/header로만 사용한다. 누락/잘못된 key/query key/foreign Origin, 옛 evolve 410 및 intake 503을 검사한다. 서버 재시작 후 doctor/catalog 재연결 및 이전 자식 정리를 확인한다. health 버전·규칙·upstream·active 슬롯, systemd 재시작/OOM, 3000 외부 차단, root/www/dev 상태를 다시 확인한다.

실 법령 호출은 이미 준비 과정에서 수행한 논리적 tool call 2회를 포함하여 전체 최대 20회 이내다. 준비 단계의 실제 HTTP 요청 수는 계측하지 않았으므로 2 HTTP requests라고 쓰지 않는다. 공식 search의 cache/후속 시행 조회/재시도 때문에 tool calls와 HTTP 수가 다르다. 후보에서 추가 실조회는 위 1회만 허용하고 실패한 법령 호출을 자동 반복하지 않는다. 실제 승인 법제처 quota를 넘길 우려가 있으면 추가 호출 전에 HOLD한다.

모두 관찰됐을 때만 `A_LIVE_VERIFIED`. 임의 LLM/Desktop 전체 지원이 검증됐다고 확대하지 않는다. B는 미완료다.

## 실패 복구

15분 초과·health/fingerprint/auth/session/조회/재시작/포트 차단 실패는 GO가 아니다. 외부 3000은 계속 닫는다.

```sh
sudo install -o root -g root -m 0600 /home/cta/cloudflared-maintenance-a.yml /etc/cloudflared/config.yml
sudo systemctl restart cloudflared.service
sudo systemctl disable --now legal-harness-a.service
sudo systemctl enable --now legal-harness-maintenance.service
```

외부 TLS와 503, localhost 3101의 응답, 구형 3000 폐쇄를 확인한다. 성공은 `maintenance_verified`, DNS/tunnel로 외부 관찰이 불가능하면 `public_port_closed/service_unavailable/recovery_unverified`다. 복구 실패나 상태 불명에서 자동 재전환하지 않는다. `/root/legal-harness-cloudflared-before-a.yml`는 증거/수동 조사용이며 구형 HTTP를 되살리는 rollback 명령으로 사용하지 않는다. 첫 안전 A가 검증된 뒤 다음 배포의 rollback artifact로 보존한다.
