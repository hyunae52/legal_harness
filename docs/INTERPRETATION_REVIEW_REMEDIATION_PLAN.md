## 1. 목적과 성공 기준

어떤 LLM에도 연결하는 공개 MCP라는 설계를 유지하면서, 실제 인용이 있어도 법적 요건을 잘못 적용하거나 반대 근거를 형식적으로 배제하는 답변을 줄인다. 추론은 연결된 LLM이 수행하고 MCP는 그 추론에 필요한 자료와 구조, 누락·모순 검사, 재검토 작업을 제공한다.

완료 결과는 다음 세 가지다.

1. 각 결론이 어떤 법적 요건, 확인된 사실, 적용 법령 버전과 날짜, 반대 근거 처리에 의존하는지 추적할 수 있다.
2. 구조 검사를 통과한 초안도 의미를 재검토하는 별도 작업을 거친다. 같은 모델의 재검토, 클라이언트가 제출한 다른 모델의 의견, 인증된 독립 검수는 구분한다.
3. 실제 답변과 검수한 답변의 차이 및 제출 분석 밖의 문장을 명시한다. 등록하지 않은 모든 쟁점을 발견했다거나 법적 정답을 인증했다고 표시하지 않는다.

외부 서버 LLM 키, 벡터 DB, 추가 유료 API, 새 사용자 수 제한은 도입하지 않는다. 기존 원문 보존·공개 조회·개인정보 비공개·교정 PR의 사람 승인 경계를 유지한다. 법률적 이유의 옳고 그름을 문자열 일치로 확정하지 않는다.

## 4. 법적 요건별 적용 계약

새 `reasoning_contract_version=2` 계약을 기존 `review_legal_reasoning`에 추가한다. 각 쟁점에 `legal_tests`, 각 주장에 `application`을 연결한다. 기존 `legal_basis`, 사실/날짜, evidence/passages를 재사용하고 새 증거 저장소는 만들지 않는다.

### 4.1 legal_tests

각 법적 요건은 안정적인 ID, 명제, 실제 근거 인용, 적용 법령 버전·날짜 역할, 유형(`prerequisite|exception|exception_to_exception`)을 갖는다. 요건의 표현과 법적 의미는 모델이 제출한 분석이다. 서버는 이 분석이 공식 법리 자체라고 인증하지 않는다.

결론에 필요한 조합을 유한한 식으로 표현한다. 연산자는 `all`, `any`, `not`, 요건 ID 참조만 허용하며 순환 참조는 금지한다. 최상위 식은 주장마다 하나다. 요건 수는 쟁점당 최대 24, 식 깊이는 4, 식 노드 수는 64로 제한하고 기존 요청 크기/세션 바이트 한도 안에서 처리한다. 상한을 넘으면 분석을 조용히 자르지 않고 분할할 쟁점과 미검수 범위를 반환한다.

이는 일반 법률 규칙 엔진이 아니다. 모델이 제출한 조건 조합과 개별 적용 선언 사이의 모순만 검사한다. 일반법/특별법·예외 관계 자체의 법적 타당성은 인용과 재검토 대상으로 남는다.

### 4.2 application

각 사용 요건에는 다음을 제출한다.

- `test_id`, `fact_ids`, `date_roles`, `citations`, 간결한 `application_reason`.
- `finding=satisfied|not_satisfied|unknown`. `unknown`은 부족한 사실/원문/적용 해석과 다음 확인을 참조한다.
- 가정 또는 미확인 사실에 의존하면 확정 충족으로 평가하지 않는다. 순수한 법률 요건은 사실 참조가 없을 수 있으나 해당 없음의 설명과 원문은 필요하다.
- 적용 범위에서 제외한 요건은 식에서 사용하는 진릿값으로 취급하지 않는다. 별도 `excluded_tests`에 근거와 이유를 기록한다. 연결된 반론/필수 요건이 있으면 기존 필요성·범위 검사를 함께 통과해야 한다.

서버의 조합 규칙은 3값 논리다. `all`은 하나라도 불충족이면 불충족, 모두 충족이면 충족, 나머지는 미상이다. `any`는 하나라도 충족이면 충족, 모두 불충족이면 불충족, 나머지는 미상이다. `not`은 충족/불충족을 뒤집고 미상은 미상으로 유지한다. 빈 `all/any`, 누락/중복 요건, 다른 쟁점의 참조, 순환·깊이 초과는 오류다.

주장은 `test_result=satisfied|not_satisfied|unknown`으로 계산 결과와 대응시킨다. 계산 결과와 다른 선언은 `blocked`. 결과가 미상인데 해당 결론을 확정하면 `blocked`. 조건부 결과는 어떤 가정을 두면 결과가 달라지는지 명시하되 원래 사실 상태는 변경하지 않는다. 요건의 참/거짓을 서버가 독립 판정한 것으로 표시하지 않는다.

기존 요건 필요성 평가와 충돌하면 더 느슨한 쪽으로 우회하지 않는다. `not_required_for_question`으로 제외된 개인 사실을 새 적용표에서 실질적으로 사용하면 필요성·출처를 다시 평가한다. 변경 후 이전 검수는 무효다.

### 4.3 공통 근거·사실 사용 검사 — LH-IR-01

서버가 v2 입력의 모든 참조 위치를 순회하여 공통 사용 목록을 만든다. 대상은 기존 주장/시점/반론/후속 처리뿐 아니라 `legal_tests`, `application`, `excluded_tests`, 충돌 양측과 해결 이유, 답변 블록, finding의 인용 및 작성자 대응이다. 클라이언트가 별도로 낸 사용 목록은 정본이 아니다. 항목에는 원래 필드 위치와 쟁점, 자료/구절 또는 사실/날짜 ID, 사용 역할을 남긴다.

사용 역할은 실제 적용·유추, 반대 근거, 배제/구별 근거, 단순 원문 소개, 후속 경과 소개를 구분한다. 모든 원문 참조는 기존 인용 일치·본문/manifest·쟁점 연결 검사를 거친다. 실제 법률 적용·배제에 쓰는 근거는 기존 법령 버전·날짜·권위 신원·적용/구별 검사에 연결한다. 적용·유추 근거는 `coreEvidenceIds`와 기존 채택/후속검색 의무에 포함하고, 반대 근거는 기존 후보·반론 처리 의무에 포함한다. 단순 소개·후속 경과라는 이유만으로 추가 후속검색을 재귀 생성하지 않지만, 같은 자료가 한 곳에서라도 실제 적용·유추로 쓰이면 그 의무가 우선한다. 역할에 관한 법적 의미 판단은 재검토 대상으로 남긴다.

검토 finding·작성자 대응에 제안된 인용은 참조와 원문 무결성을 확인하되 현재 답변의 채택 근거와 구분한다. 제안을 실제 적용 근거로 수용하면 새 artifact에 반영하고 그때 채택/후속검색 의무를 다시 계산한다. 검토 의견 저장만으로 현재 분석에 근거를 몰래 추가하지 않는다. 미확인 사실이 오류라는 지적 자체를 미확인 사실의 확정 사용으로 취급하지 않는다.

기존 필드에서 새 필드로 동일 참조를 옮겨도 필요한 검사가 사라지지 않아야 한다. 새 핵심 근거가 생기면 기존 채택 장부와 의무를 먼저 갱신하고 그 최종 상태로 구조검수한다. 모든 사용 사실·날짜는 존재·쟁점·필요성·확인 상태를 검사한다. 미확인 사실을 전제로 한 예외를 `not_satisfied`로 제출해 `not`으로 뒤집어도 확정 결론으로 승격하지 않는다. 가정/미상을 사용하는 leaf의 확정 선언은 거부하고 `unknown`과 가정별 조건부 분석을 요구한다.

## 5. 근거 충돌과 반론 검토

### 5.1 충돌 장부

`authority_conflicts`는 같은 쟁점에 관하여 양립하지 않는 법적 명제의 쌍, 관련 요건/주장 ID, 양측 원문 ID, 적용 법령·날짜·사실 차이, 채택/배제/미해결과 이유를 기록한다.

충돌 여부 자체는 모델의 제안이며 서버가 모든 충돌을 발견했다고 주장하지 않는다. 기존 서버 후보 장부의 필수 후보 처리 의무는 유지한다. 모델이 비교 대상으로 등록한 반대 근거나 필수 후보를 장부에서 빼도 현재 검토 완료로 승격하지 않는다.

자동 우선순위 점수는 만들지 않는다. 채택 이유에는 동일 쟁점·규정 여부, 개정·부칙, 사실 차이, 후속 판결 또는 해석 확인을 연결한다. 일반법/특별법 주장에도 그 관계의 출처가 필요하다. 법령 문구와 달라 보인다는 이유만으로 판례를 버릴 수 없고, 대법원이라는 이유만으로 다른 적용 법령의 결론을 가져올 수도 없다.

### 5.2 반론 재검토

현재 원문에서 결론을 가장 강하게 반박할 수 있는 자료와 논리를 모델이 골라 기록하게 한다. 검색 0건일 때는 가짜 반대 판례를 요구하지 않는다. 이 경우 법적 요건/예외의 반대 적용 가능성을 검토하고, 확인한 범위와 남은 검색 한계를 남긴다.

`resolved`에는 해소 근거 인용과 해당 요건·사실 차이를, `distinguished/irrelevant`에는 구별의 기준과 실제 사건 사실/원문을 연결한다. 이유 문자열 길이만으로 해소 여부를 인증하지 않는다. 미해결 충돌이 결론의 사용 요건을 바꿀 수 있으면 확정 결론을 막고 조건부/유보로 반환한다. 요청 밖 독립 안내는 기존 scope track으로 분리하며 자동으로 본질문 전체를 차단하지 않는다.

## 6. 답변 전체와 재검토 결과 결합

### 6.0 현재 분석의 저장과 내용 결합 — LH-IR-02

현재 `last_review`는 해시만 저장하므로 이를 packet 원본으로 삼지 않는다. v2 `review_legal_reasoning`이 정규화한 분석·적용표·충돌·범위 평가·답변 블록을 하나의 현재 `reasoning_artifact`로 저장한다. 인용은 기존 원문 ID/구절을 참조하며 원문 본문을 복제하지 않는다. 스키마·참조 오류는 저장하지 않고, 유효한 입력의 구조검수 결과와 artifact를 원자적으로 함께 저장한다. 공간이 부족하면 기존 artifact·결과가 유지된다. `prepare_reasoning_review`는 저장된 artifact ID/hash만 지정하며 별도 초안이나 분석을 덮어쓸 수 없다. 구조상 공백이 있는 artifact도 재검토 대상으로 제공할 수 있으나 readiness는 구조 완료 전까지 false다.

v2 구조검수와 packet은 동일한 `review_content_hash`를 사용한다. 그 입력은 계획과 사실·날짜/범위 관계, 현재 필요성 평가와 미매핑 이력, 유효한 원문·manifest·쟁점 연결, 검색 결과/후보/채택 관계 등 coverage에 영향을 주는 관측, 현재 artifact 전체, 정책·계약 버전이다. 필드 순서는 정해진 직렬화 규칙을 쓰되 답변 순서와 원문 문자열은 그대로 보존한다. 내용의 일부가 기존 검사에서 쓰이면 이 hash에서도 누락하지 않는다.

packet 발급 정보, 자료 제공 기록, 요청 영수증, 검토 의견 저장 같은 관리 정보와 단순 `state_version` 증가는 내용 hash에서 제외한다. 진행 중 작업·만료는 hash 외 별도 유효성 조건으로 검사한다. 신규 조회 결과·검색 실패/완료 관측이나 같은 revision의 필요성 평가·범위 연결 변경은 내용 변경이다. 따라서 결과적으로 답변 문구가 같아도 이전 v2 구조검수와 모델 재검토의 현재 효력은 무효다. v1의 `last_review.current`와 snapshot 의미는 유지하고, v2 readiness는 별도 내용 결합 구조검수 기록을 사용한다. 오래된 결과를 무시하고 통과시키거나 버전 숫자만 고쳐 효력을 되살리지 않는다.

### 6.1 답변 블록

버전 2에서는 자유 `draft_answer`와 별도 주장 목록 대신 `answer_blocks`를 정본으로 사용한다. 블록은 `claim|source_quote|context|uncertainty|next_step`이며 ID·본문·쟁점 ID·관련 주장/요건/근거 ID를 가진다. 서버가 순서대로 본문을 결합하고 이를 `draft_answer` 및 기존 hash와 비교한다. 불일치하면 어떤 블록 밖 문구가 추가되었는지 반환하고 검수 완료를 거부한다.

주장 블록마다 요건 적용 결과와 근거가 필요하다. 인용 블록은 실제 원문을 대조한다. 나머지 블록도 재검토 packet에 전부 넣는다. `context`에 법적 결론을 숨기는 의미상 오분류는 결정론적 검사로 완벽히 판별할 수 없으므로 모델 재검토 항목과 평가 사례에 포함한다. 단순 문장 분리기·키워드만으로 모든 주장을 찾았다고 표시하지 않는다.

최종 답변의 검수 효력은 정확히 같은 블록/문구에만 적용된다. 클라이언트가 이후 덧붙이거나 바꾼 답변은 미검수다. MCP가 대화창의 모든 출력을 통제할 수 없다는 경계를 사용자 안내에 남긴다.

### 6.2 재검토 packet

새 `prepare_reasoning_review` 도구가 서버에서 현재 snapshot에 결합된 packet ID를 발급한다. packet에는 사실·미상·날짜, 사용 원문의 원래 요건/예외 맥락, 적용표, 충돌 장부, 전체 답변 블록과 기존 공백을 포함한다. 원문은 명령이 아닌 검토 자료로 취급한다.

크기 한도를 넘으면 원문 manifest를 참조하는 packet 전용 페이지를 사용하며 누락 목록과 읽어야 할 페이지를 명시한다. 본문을 몰래 자른 packet은 완료되지 않는다. quote만 고립해서 보여주지 않고 실제 인용이 속한 서버 원문 unit 전체를 맥락으로 포함한다. 분할 저장된 unit은 manifest의 해당 범위를 모두 연결한다. 원천 제공자가 반환하지 않은 부분은 계속 공백이며 맥락을 확보했다고 표시하지 않는다.

packet 결합값: actor/연구 ID, revision, issued_state_version, artifact ID, review_content_hash, packet 내용 manifest hash, policy/계약 버전, 만료 시각. 원문을 포함한 packet을 GitHub·로그·외부 서비스에 자동 게시하지 않는다.

packet manifest에는 이번 라운드에서 다룰 이전 finding과 작성자 대응의 hash도 포함한다. 그 대응이 바뀌면 새 packet이 필요하지만 구조검수 내용까지 바뀐 것이 아니면 v2 구조검수는 유지한다. 하나의 packet에는 의미 검토 제출을 한 번만 수락한다. 수락 뒤에는 결과 조회만 허용하고 다른 request_id로 두 번째 의견을 덮어쓰지 않는다. 같은 요청의 재전송은 영수증을 반환하며, 다음 검토에는 현재 finding 집합을 담은 새 packet이 필요하다. 수락된 packet은 제출 자체 때문에 stale이 되지 않으며 해당 결과의 현재 효력은 내용·정책·수명·열린 finding으로 판단한다.

`issued_state_version`은 발급 이력이며 이후 검수 메타데이터 저장만으로 packet이나 v2 구조검수를 stale로 만들지 않는다. 명시적인 새 변경/준비/제출 요청은 `expected_state_version`도 비교한다. 이미 수락한 요청의 재전송은 §7의 영수증 조회 예외를 적용한다.

### 6.2.1 자료 제공 범위 — LH-IR-03

packet 생성 완료와 검토 자료 제공 완료는 별개다. 서버가 `required_units` manifest를 고정한다. 여기에는 전체 답변 블록·적용표·사실/날짜·공백·충돌/열린 finding과 위 원문 맥락이 들어간다. `provided_units`는 해당 actor의 동일 packet/내용 hash에 대해 성공 응답으로 생성한 완전한 단위만 기록한다. 준비 응답에 실제 포함한 단위도 인정하지만 단순 index·요약·원문 ID, 다른 packet에서 읽었던 자료, 실패·부분 응답은 인정하지 않는다. 이는 서버의 자료 제공 관측이지 네트워크 도달·실제 이해의 인증이 아니다.

`get_legal_research`에 packet 페이지 조회 분기를 추가한다. cursor는 actor/연구, packet ID, 불변 manifest hash, offset에 묶으며 일반 원장 페이지의 `state_version` cursor와 구별한다. 동일 페이지 재조회는 같은 자료를 반환하고 제공 이력은 집합 합치기로 원자 처리한다. 이 관측 기록은 내용 hash/검토 횟수를 바꾸지 않으며 클라이언트 내용 변경 CAS를 요구하지 않는다. 관리 상태 버전이 변해도 같은 packet의 다음 페이지는 유효하고, 실제 내용 변경·packet 교체·만료는 거부한다.

필수 단위가 남으면 `submit_reasoning_review`는 `REVIEW_MATERIAL_INCOMPLETE`와 누락 목록을 반환하며 완료 의견으로 수락하거나 횟수를 차감하지 않는다. 부족한 자료를 제공한 뒤 다시 검토·제출해야 한다. 자료 제공 완료만으로 `model_review=recorded`나 readiness를 만들지 않는다. 검토 도구·클라이언트 안내에서도 이 순서를 따른다.

### 6.3 재검토 제출

새 `submit_reasoning_review`는 정확한 packet ID·결합값에 대하여 요건 누락, 잘못된 사실 대응, 인용 의미 역전, 부정/예외 탈락, 반대 자료의 부당한 배제, 본문 미등록 주장, 결론 강도의 문제를 제출한다. 각 finding은 대상 ID, 해당 본문/원문 구절, 문제 설명, 제안 변경 또는 필요한 자료, `open|disputed|resolved` 상태를 가진다.

허용 결과는 `revise|qualified|no_detected_issue`다. 결과는 검수 주체의 의견이며 법률 정답 PASS가 아니다. 같은 LLM의 새 검토는 `self_review`; 클라이언트가 다른 모델이라고 주장해도 `client_reported_review`로 표시한다. 클라이언트가 이름·모델명·다른 session 값을 보내는 것만으로 독립 검수 상태가 바뀌지 않는다.

결과와 실제 finding 집합은 아래 표로 함께 검사한다. 상충하는 제출은 `REVIEW_RESULT_CONFLICT`로 거부하고 완료 의견/횟수로 수락하지 않는다. 결론 영향 여부는 등록된 쟁점·요건·답변 블록·scope 의존 관계로 평가하며 의미적 분류의 한계는 공개한다.

| 결과 | 수락 조건 | ready_for_answer |
| --- | --- | --- |
| `revise` | 새 finding 또는 명시적으로 다시 다룬 이전 미해결 finding이 최소 하나 있음 | 항상 false |
| `qualified` | 조건/한계를 현재 답변의 특정 블록에 연결하고, 본질문·의존 쟁점의 차단 finding을 모두 처리함 | 그 조건이 결합된 답변에 실제 포함되고 나머지 §7 조건도 충족할 때만 true |
| `no_detected_issue` | 본질문·의존 쟁점에 새 미해결 finding이나 이전 차단 finding이 남지 않음 | 나머지 §7 조건도 충족할 때만 true |

아직 필요한 사실·원문이나 미해결 법리 충돌을 단순 `qualified` 조건으로 옮겨 기존 구조 공백을 지울 수 없다. 해당 구조검수가 `needs_info`라면 readiness는 계속 false다. 요청 밖 독립 안내의 미해결 기록은 별도로 표시하며 기존 scope 기준으로 본질문과의 의존성이 없다는 연결을 유지한다.

인증된 독립 검수의 완료 상태는 현재 출시 범위에 추가하지 않는다. 이후 서버가 신뢰하는 별도 실행자와 동일 snapshot의 실행 증거가 갖춰질 때만 별도 설계로 도입한다. 기본 배포는 서버 LLM을 실행하지 않으므로 독립 의미 검수는 `not_configured`, 의미적 지지는 `unverified`를 유지한다. 모델 재검토 기록을 구조 검사 결과와 별도 필드로 제공한다.

### 6.4 수정과 반복

미해결 finding이 결론의 전제 또는 강도에 영향을 주면 `ready_for_answer=false`다. 초안 작성 모델은 finding에 수용/반박과 원문 근거를 제출한다. 반박 사실만으로 `resolved`로 바꾸지 않는다. 수정된 답변은 새 hash와 packet으로 재검토하고, 사실·날짜·근거 변경에는 기존 revision/후속검색 규칙도 적용한다.

최초 제출에서 finding은 `open`으로 생성한다. 작성자의 대응은 `proposed_fix|disputed`로 따로 기록하고, 다음 검토가 같은 finding ID를 다시 다뤄 `resolved|open` 의견을 제출해야 닫힘을 계산한다. 다음 검토에서 누락한 이전 finding은 열린 채로 남는다. 누가 다시 검토했는지는 계속 자기신고/셀프 검수 수준으로 표시하며 이 왕복만으로 독립성이나 해석의 정답을 인증하지 않는다. 계약·인용 오류처럼 서버가 직접 확인하는 finding은 해당 결정론적 검사도 다시 통과해야 한다.

숨은 주장 지적은 주장 ID가 없어도 답변 블록/구절과 내용 hash로 연결한다. 대상 삭제·ID 교체·scope 이동으로 매핑이 끊긴 finding은 `unmapped` 미해결로 유지하고 본질문 readiness를 기본 차단한다. 작성자는 새 대상 연결 또는 삭제/범위 변경의 이유를 제안하고, 다음 검토가 같은 ID에 대해 명시적으로 재대응해야 한다. 삭제로 문제가 사라졌다는 검토는 가능하지만 자동 닫힘은 아니다. 독립 안내로의 재분류도 기존 scope 관계와 근거를 검토하며, 대상 ID가 없다는 이유만으로 비차단 처리하지 않는다. 이는 LH-IR-04의 처리 우회를 막는 계약이다.

한 번의 사건 답변에서는 기본 재검토를 1회 수행하고, 수정이 있으면 최대 2회 추가 검토한다. 한도 뒤 미해결 사항은 조건부/유보 답변으로 표시한다. 오류·시간 초과·응답 없음은 검수 완료가 아니다. 실사용 런타임이 통과할 때까지 무한 호출하게 만들지 않는다. 이번 개발 계획에 대한 Pro 검수 반복과 이 런타임 한도는 별개다.

## 7. 상태와 호환성

외부 반환 상태를 다음처럼 분리한다.

| 필드 | 뜻 |
| --- | --- |
| `status` | 기존 `blocked|needs_info|structurally_complete` 유지. 근거·검색·적용 구조 결과 |
| `reasoning_contract_version` | 실제 검사한 계약 버전. 누락 시 기존 계약으로만 검사 |
| `answer_binding` | 전체 블록 결합 일치/불일치와 검수한 답변 hash. 대화창 최종 출력 보증 아님 |
| `model_review` | `not_requested|pending|recorded|stale|failed`, 주체와 finding/결과. 법적 승인 아님 |
| `ready_for_answer` | 동일 내용 hash의 v2 구조 완료, 현재 packet의 필수 자료 제공 완료·수락된 `qualified/no_detected_issue`, 현재 유효한 답변 결합, 차단/미매핑 finding 없음, 미만료·진행 중 작업 없음일 때만 true |
| `legal_verification`, `semantic_support` | 계속 `unverified`. 구조 완료나 모델의 동의를 정답 인증으로 바꾸지 않음 |
| `independent_review` | 기본 `not_performed`. 클라이언트 제출만으로 승격 금지 |

`ready_for_answer=false`는 사용자의 답변 자체를 금지한다는 뜻이 아니다. 공백을 밝힌 조건부/유보 답변은 가능하며 완료된 검수 결과처럼 표시하지 않는다. 버전 1 요청은 계속 수용하되 `ready_for_answer`를 true로 부여하지 않고 버전 2 미수행을 명시한다. 단순 원문 조회에 연구 세션·적용표·인터뷰를 강제하지 않는다.

기존 actor 격리, revision/state_version, busy/만료, 재시도·중복 방지 계약을 재사용한다. 새 도구는 같은 연구 서비스와 MCP/REST 계약으로 노출한다. packet 준비/제출은 별도의 원문 검색 호출을 하지 않는다. 각 제출은 원자적으로 저장하고 저장 용량 초과로 실패하면 직전 기록이 유지된다. 기존 한도에서 새 메타데이터가 들어갈 최소 공간을 확보하고 한도 소진 시에도 저장된 자료 조회·공백 답변은 가능하게 한다.

### 7.1 재전송·횟수·보관 — LH-IR-05

두 새 도구는 `request_id`와 원래 요청 전체의 입력 hash를 사용한다. 입력 hash에는 최초 `expected_revision/expected_state_version`도 포함한다. 처리 순서는 (1) 인증·소유권·세션 수명 확인, (2) 수락된 요청 영수증 조회, (3) 영수증이 없는 새 요청에 revision/CAS·busy·현재 packet·제공 범위·횟수 검사를 적용, (4) 결과·영수증·횟수를 원자 저장이다. 같은 ID·동일 입력은 오래된 CAS라도 mutation을 재실행하지 않는 영수증 조회이고, 같은 ID·다른 입력은 충돌이다. 신규 요청의 오래된 CAS는 계속 거부한다.

영수증에는 도구/요청 ID, 원래 입력 hash, 당시 packet/내용 hash, 종료 결과·binding/finding 식별자, 당시 버전, 검토 순번을 보존한다. 재전송 응답은 `replayed`와 이 처리 결과를 돌려주며 현재 연구 상태와 구별한다. 동일한 대용량 원문/page 바이트를 다시 보관하거나 옛 응답의 ready=true를 복사하지 않는다. P1→P2→P3 이후 P1 재전송은 과거 처리 영수증일 뿐이며, 현재 효력·ready 값은 현재 상태에서 다시 계산한다. 만료·삭제된 연구나 다른 actor에는 과거 영수증도 노출하지 않는다.

세션에는 현재 artifact/packet 하나와 직전 packet의 최소 식별 이력, 해당 연구 수명 동안 수락한 prepare/submit 요청의 작은 영수증들을 보관한다. 성공한 요청 ID는 살아 있는 세션에서 조용히 퇴출하지 않는다. 공간이 부족하면 새 요청을 수락하기 전에 명시적으로 거부한다. 미해결 finding은 새 packet으로 이관하고 원래 ID·근거 hash를 유지한다. 현재 자료와 영수증·제공 이력·finding 모두 기존 세션/요청 바이트 상한에 포함하며 원문 본문을 중복 저장하지 않는다.

최대 3회는 연구 ID에 결합된 서버 소유 검토 계보의 수락된 의미 검토 제출 횟수다. revision, 새 request_id, packet 교체, 작성자 수정/반박, 페이지 조회로 초기화하지 않는다. 재전송은 횟수를 늘리지 않으며, 스키마 오류·CAS 충돌·자료 미전달처럼 수락하지 않은 제출도 차감하지 않는다. 준비 후 내용이 바뀌면 새 packet이 필요하지만 준비 자체가 의미 검토 횟수를 소비하지 않는다. 모델에게 한도를 피해 새 연구를 만드는 동작은 안내하지 않는다. 서로 다른 공개 연구가 실제로 같은 사건인지 서버가 자동 식별한다는 보장은 하지 않는다.

추가 세부 크기 상한은 구현 전 정상 흐름 계측으로 정하고, 기존 한도 안에 검토 기록 저장 공간을 확보한다. 상한 실패를 검수 성공으로 바꾸거나 기존 원문·열린 finding·수락 영수증을 조용히 버리지 않는다. 단순 원문 조회에는 이 연구 계약을 강제하지 않는다.

서버는 도구를 호출하지 않은 LLM 답변을 감시하지 못한다. 설치 안내에는 사건 판단 시의 v2 도구 순서를 명시하며 일반 조회와 구별한다. 검수 완료 여부는 서버가 발급한 결과와 결합된 답변에만 표시한다.

## 8. 트리거와 책임 분리

기존 QG 키워드는 질문 후보 생성에만 사용한다. 후보 적용 상태를 `candidate|applicable|not_applicable|unknown`으로 나누되 문자열에 “아니다”가 있다는 이유만으로 자동 제외하지 않는다. 명시적 쟁점·확인된 사실·범위 연결이 우선이며, 제외에는 사실 또는 원문 연결과 이유를 요구한다. 모델이 제시한 관련 쟁점도 후보로 받을 수 있지만 법적 규칙이나 정답으로 자동 승격하지 않는다.

두 QG가 겹치면 동일 사실 질문을 ID로 합치고 서로 다른 필요한 질문은 유지한다. 질문 룰의 중복과 일반법/특별법의 법적 충돌을 같은 우선순위 엔진으로 처리하지 않는다. 명시적 프로필과 필수 원문 검색을 키워드 불일치로 끄지 않는다.

새 코드의 책임은 `reasoningContracts`, `reasoningApplication`, `reasoningConflicts`, `reasoningReviewPacket`, `reasoningReviewState`의 좁은 모듈로 나눈다. 필요 이상으로 파일을 만들지 않고 공통 계약·순수 검사를 우선한다. ResearchService는 actor/세션·원자적 상태 변경을 소유하고 순수 검사에 필요한 읽기 전용 입력을 전달한다. 저장과 비동기 실행 분리는 회귀 계약이 고정된 뒤 수행하며, 법적 의미 개선과 대규모 재작성의 배포를 묶지 않는다.

### 품질 평가와 정답 한계

구조 검사 시험과 법률 해석 품질 평가는 분리한다. 합성 법령/사건으로 고정한 폐쇄형 사례에서 누락된 예외, 실제 원문 인용을 이용한 의미 역전, 사건일·개정 적용 오류, 반론의 부당한 배제, 미등록 결론, 과도한 유보를 포함한다. 최소 12개 사례, 각 3회 실행하며 같은 제공 자료·모델·설정으로 기존/신규 흐름을 비교한다. 반복 출력은 독립 사례 수로 부풀리지 않는다.

정답/오류 rubric은 실행 전에 고정하고 모델에게 정답을 보여주지 않는다. 기존 실패의 문구만 외운 성능을 피하도록 의미가 같은 다른 표현과 새로운 사실 조합의 보류 사례를 최소 4개 포함한다. 평가자는 출력 순서/기존·신규 표시를 숨긴 결과로 판정하고, 모호한 사례는 정답 확정이 아니라 판정 보류로 기록한다.

평가는 두 묶음으로 나눈다. 첫째는 의도적으로 오류를 넣은 동일 초안을 주고 기존/신규 검수의 탐지 차이를 비교한다. 둘째는 정상·조건부 답변이 가능한 사건을 처음부터 처리하여 과도한 유보와 추가 호출 비용을 비교한다. 동일 사례·반복의 짝을 유지하며 모델 버전·설정·입력·원문·도구 호출·최종 결과를 기록한다. 프롬프트가 다른 비교는 의도된 워크플로 차이로 표시한다. 어느 묶음에서도 자체 생성 정답이나 생산 코드 계산값을 oracle로 쓰지 않는다.

출시 판단 기준: 결정론적 계약 시험 전부 통과, 각 치명적 오류 유형을 실제로 탐지하는 사례 존재, 보류 사례의 확정 오답 수 증가 없음, 정상 사례의 정당한 확정·조건부 답변 가능률이 기존보다 낮아지지 않음, 오류 주입 묶음에서 결론을 바꾸는 오류의 미탐지 건수 감소. 기존 미탐지가 0이면 감소를 요구하는 대신 신규도 0을 유지하고 별도의 오류 노출 사례로 탐지 능력을 증명한다. 구조 통과율·테스트 수·의미 검수자의 PASS 비율은 품질 지표로 대체하지 않는다. 모델이나 실제 실행 접근이 없으면 품질 개선은 미검증으로 남기고 “해석 품질 검수 완료” 출시는 보류한다. 검수자의 의견이 갈리면 사람의 판정 전까지 해당 사례는 품질 PASS의 근거에서 제외하고 미해결 수를 공개한다.

실제 법률 사례는 별도 원문·사실관계·적용일 검토를 거쳐야 정답 oracle로 쓸 수 있다. 이번 계획에서 특정 세금 사건의 실체법상 결론을 새로 확정하지 않는다. 실제 사례 검수는 해당 시점 공식 자료와 사람의 검토를 추가로 확보한 뒤 기록한다.

## 10. 구현·검수·배포 순서

1. 이 계획과 시험 계약에 대해 Pro의 PLAN PASS를 확보한다. 지적별로 수용/보완/근거 있는 반박을 기록하고 변경한 정확한 문서를 재검수한다.
2. 별도 구현 단계에서 A의 계약 시험을 먼저 고정하고 의미 있는 RED→GREEN을 확인한다. 기존 coverage/applicability 검사는 유지한다.
3. B와 C를 구현하고 동일 snapshot의 end-to-end 연구·답변·재검토·수정 흐름을 합성 provider로 검증한다. 외부 모델이 실제 수행한 기록과 mock 시험을 구분한다.
4. D와 E를 진행한다. 관련 회귀 후 `npm run review`, `npm run review:package`, `npm run audit:runtime`, 기존 secret scan을 정확한 후보에 실행한다. 유효한 동일 후보 증거는 재사용한다.
5. 코드 검수·품질 평가가 통과한 후보로 PR을 만든다. 최종 머지 승인과 운영 배포는 그 단계의 사용자 지시·기존 정책에 따른다. 이번 PLAN PASS를 배포 승인으로 사용하지 않는다.
6. v2 기능 플래그를 기본 off로 두고 제한된 시험에서 공개 조회/구 계약 영향과 복구를 확인한 후 활성화한다. 플래그를 꺼도 저장된 v2 연구를 v1 통과로 재분류하지 않는다. 안전한 구 계약 조회 또는 명시적인 v2 재시작 안내만 허용한다.

## 11. Pro 검수 요청과 반복 기준

검수자는 계획 전체와 명시된 기준 소스만 읽고 PLAN PASS / PLAN REVISE / PLAN UNVERIFIED 중 하나를 반환한다. 계획 단계에서 미구현이라는 이유만으로 CODE FAIL을 요구하지 않는다. 반대로 검수 자료가 읽히지 않거나 중요한 계약이 구현 가능하게 정의되지 않았다면 PASS로 표시하지 않는다.

중점 검수: 셀프 검수의 독립성 과장, 의미 검수 공백을 형식 필드로 숨기는 문제, 조건 조합·예외 처리 오류, 조문/사건일/반론 연결 우회, context 문장에 결론 숨김, stale 결과와 클라이언트 위조 검수, 호출·용량 폭증, 구 계약/일반 조회 회귀, 검증 oracle와 출시 기준의 실현 가능성.

각 지적에 심각도, 문서 절, 구체적 반례, 최소 보완과 시험 기준을 요청한다. 유효한 지적을 반영한 뒤 새 문서 hash에 대해 재검수한다. 사용자는 통과할 때까지 반복을 요청했다. 기술적 미해결점을 피하려고 다른 검수자로 바꾸지 않는다. 로그인/접근 차단·불완전 응답은 검수 실패와 구분하여 기록하고, 실제 응답 없는 PASS를 만들지 않는다.
