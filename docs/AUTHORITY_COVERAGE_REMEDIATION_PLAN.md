## 1. 해결할 문제와 목표

현재 하네스는 모델이 제출한 자료·주장 사이의 연결을 검사한다. 제출하기 전에 어떤 자료를 찾아야 하는지, 실제로 그 검색을 수행했는지는 충분히 검사하지 않는다. 따라서 법령과 같은 방향의 국세청 해석만 모은 답변이 상반되는 대법원 판례를 찾아보지 않은 채 구조 검수를 통과할 수 있다.

이번 수정의 목표는 **사건 판단에 필요한 자료군의 조회와 주요 반대 근거의 검토가 빠진 상태를 서버가 미완료로 판정하는 것**이다. 스킬의 주의 문구에만 의존하지 않고, 실제 도구 호출·원문·조회 범위를 검사 근거로 삼는다.

다음 원칙은 유지한다.

- 사용자가 선택한 LLM이 추론과 답변을 담당한다. 일반 MCP 사용에 서버용 LLM API 키를 추가로 요구하지 않는다.
- 공개 MCP와 단순 법령 조회는 계속 제공한다. 접속키나 새로운 사용자 수 제한을 도입하지 않는다.
- 사건에 적용되는 법령·부칙을 기준으로 판례·행정해석을 교차 검토한다. 대법원이라는 이유만으로 법령 개정이나 사실 차이를 무시하지 않는다.
- 검색 수행 완료, 원문 확보, 법률적 타당성, 독립 AI 검수는 서로 다른 상태로 표시한다.
- 교정 PR은 기존의 공개 내용 확인·생성 동의 절차를 사용한다. 실제 고객 사실이나 조사 원문을 자동 게시하지 않는다.

기존 정책은 [근거 우선순위](EVIDENCE_PRIORITY.md)를 따른다. 이 문서는 그 정책에서 부족했던 **검색 범위·출처 분류·실행 확인**을 보완하는 후속 계획이다.

## 3. 서버가 강제할 범위

| 사용 형태 | 적용 기준 |
| --- | --- |
| 조문·문서 단독 조회 | 기존 도구를 사용한다. 결과는 조회 자료이며 사건 검수 완료 표시는 없다. |
| 사실관계가 있는 사건 판단 | 연구 세션에 필수 조회 의무를 생성하고, 최종 구조 검수에서 수행 여부를 검사한다. |
| 자료·사실이 미완성인 사건 | 가능한 범위의 조건부 설명과 다음 확인 사항을 제공한다. 확정 결론용 검수는 통과시키지 않는다. |
| MCP 밖에서 작성한 LLM 답변 | 서버가 발언 자체를 차단할 수 없다. 클라이언트별 검수 호출 지침과 실행 평가로 확인한다. |

**조회 도구만 호출한 답변을 서버 검수 완료라고 표시하지 않는 것**이 B-01의 실현 가능한 목표다. 모든 LLM의 자유 발화를 MCP 서버가 통제한다고 약속하지 않는다.

`structurally_complete`라는 기존 응답 형식은 유지하되 사건 판단 경로의 검사 항목을 확대한다. `legal_verification=unverified`, `semantic_support=unverified`는 계속 유지한다. 새 결과에는 자료군별 수행 여부와 남은 공백을 함께 반환한다.

## 4. 필수 조회와 결과 0건 처리

### 4.1 사건별 조회 의무

서버 정책이 등록된 쟁점마다 조회 의무를 생성한다. 모델이 `required=false`라고 선언하거나 `authorities` 배열을 비워서 의무를 제거할 수 없게 한다. 자료 종류별 적용 범위는 서버가 관리하는 정책으로 정한다.

| 자료군 | 사건 판단에서 확인할 내용 |
| --- | --- |
| 적용 법령 | 사건의 날짜 역할에 맞는 조문·위임 규정·필요한 부칙과 버전 |
| 법원 판례 | 해당 조문·요건의 중립 검색과 잠정 결론을 뒤집을 수 있는 검색. 적용 가능한 대법원 판단을 확인할 수 있는 검색 범위를 포함 |
| 행정해석·심사/심판 | 세법 사건은 해당 국세·지방세 자료군을 조회하고 법원 판단과 구분. 세법 밖의 분야에는 해당 분야 정책을 적용 |
| 후속 처리 | 인용하는 핵심 판례·해석의 상급심, 파기·변경, 후속 해석, 관련 법 개정과 적용 관계 |

판례와 행정해석은 서로 다른 자료군이다. 동일한 질의회신을 여러 번 조회하거나 두 제공자가 같은 데이터베이스를 조회한 것을 독립된 교차 검증으로 세지 않는다.

검색어는 조문·법령 식별자와 쟁점의 법적 요건을 포함한다. 중립 검색과 반대 가설 검색을 구분하되 특정 예상 결론만 반복하는 검색어를 기본값으로 만들지 않는다. 사건일 이후 선고된 판례도 검색하며, 사건일을 선고일 검색 상한으로 자동 설정하지 않는다.

제공자의 실제 도구 스키마와 법원·날짜 필터 지원을 먼저 확인한다. 요청한 필터가 지원되지 않았는데 대법원 검색을 완료한 것으로 표시하지 않는다. 사건 검색에서는 공식 원천의 인덱싱 범위도 미확인 사항으로 남긴다.

### 4.2 상태 구분

| 관측 상태 | 의미 | 완료 처리 |
| --- | --- | --- |
| `not_attempted` | 필수 검색을 실행하지 않음 | 미완료 |
| `failed` | 오류·접근 실패·시간 초과 | 미완료, 대체 경로 또는 재시도 |
| `partial` | 본문·검색 결과·페이지가 잘렸거나 필요한 조회 범위가 남음 | 해당 공백을 해결하기 전 미완료 |
| `completed_with_candidates` | 검색에 성공하여 후보 자료를 확보 | 주요 후보의 원문·적용 관계 검토까지 필요 |
| `completed_no_candidate` | 정해진 범위의 검색은 성공했으나 후보를 찾지 못함 | 검색 수행 의무의 충족과 판례 존재 여부 판단을 구분 |

0건을 처리할 때는 정규화한 검색어, 자료군·필터, 조회 시각, 페이지 범위, 제공자 성공 응답을 남긴다. 너무 좁은 첫 검색이 0건이면 검색어를 넓히거나 다른 경로로 보완한다. 대체 경로가 같은 원천을 쓰는지도 기록한다.

충분히 정한 범위에서 검색이 끝났다면 **실제로 존재하지 않는 반대 문서를 제출하도록 강요하지 않는다.** 현재의 `counter` 문서 개수 검사를 보완하여 반대 검색 완료·후보 없음 상태를 표현한다. 다만 그 상태는 ‘반대 판례가 존재하지 않는다’는 증명이 아니며, 그런 단정의 근거로 사용할 수 없다.

검색 0건만으로 언제나 법률 결론을 유보시키지는 않는다. 근거의 성질과 남은 공백을 표시하고 기존 법령·사실·반론 검사를 계속 적용한다. 필요한 원문을 찾았지만 읽지 못한 경우는 후보 없음으로 바꿀 수 없다.

### 4.3 조회 의무 생성과 검색 기록 수락 계약 — Pro P1-1 반영

연구 세션의 모든 등록 쟁점에는 기본적으로 적용 법령 확인·중립 판례 검색·반대 가설 판례 검색 의무를 만든다. 단순 조회의 기존 경로는 그대로 둔다. 세법 자료군은 관측한 법령 식별자가 서버의 버전 있는 국세·지방세 분류표에 속하거나 해당 사건 프로필이 활성화되면 추가한다. 프로필이 없다는 이유로 공통 판례 의무를 제거하지 않는다. 분야나 조문 앵커가 미확정이면 `anchor_pending` 준비 공백을 남기고 예비 법령 조회를 진행한다. 모델이 분야를 `other`로 바꾸는 것만으로 이미 생성된 의무가 없어지지는 않는다.

앵커는 실제 법령 receipt의 법령 ID·조문·버전과 등록 쟁점을 연결한다. 법령의 신원·버전 관측과 **그 법령이 쟁점에 맞는다는 모델의 판단**은 구분한다. 앵커 확정 후 서버가 정책 버전·앵커·검색 목적별 `recipe_id`와 필수 단계를 생성한다. 미지원 분야·필터·조회 경로는 공백으로 반환하며, 빈 의무 집합을 완료로 해석하지 않는다.

| 단계 | 서버가 생성·확인할 조건 | 완료로 세지 않는 경우 |
| --- | --- | --- |
| 중립 검색 | 관측 법령명/ID·조문과 쟁점 요건을 사용한 지정 템플릿. 사건일로 판례 선고일 상한을 만들지 않음 | 앵커 없음, 다른 법령·자료군, 결론만 반복한 임의 검색 |
| 반대 가설 검색 | 같은 앵커에 별도로 등록한 배제 요건·예외·요건 충족 시점을 확인하는 템플릿 | 공백·어순 차이만 있는 중립 검색을 재제출. 지정 템플릿이 없으면 `recipe_unavailable` |
| 0건 보완 | 초기 질의가 0건이면 서버 템플릿으로 세부 사실·제약어를 제거한 앵커 중심 질의를 1회 이상 수행 | 모델이 보완했다고 선언한 경우, 최초의 좁은 질의만 0건인 경우 |
| 후속 검색 | 문서 식별자·사건 연결과 같은 조문 앵커를 사용한 후속 처리 및 개정 조회 | 동일 문서 본문만 재조회, 다른 문서의 후속 검색 |
| 제공자·페이지 | 실제 적용된 필터, 원천 자료군, 후보 목록 파싱, 응답 종료/다음 페이지를 관측 | 미지원 필터, 알려진 잔여 페이지, 파싱 실패·범위 미상·오류를 0건으로 변환 |
| 복합 도구 | 자료군별 요청·성공/실패·후보·범위가 각각 관측되는 하위 기록만 연결 | 법령만 성공한 복합 응답으로 판례까지 완료, 내부 호출 정보가 없는 요약 응답 |

첫 구현은 질의당 최대 2페이지, 0건 보완 질의는 1단계로 제한한다. 페이지 한도에서 다음 페이지가 남으면 `partial`이며 임의로 종료했다고 쓰지 않는다. 필수 단계가 정상 종료되고 후보가 없을 때만 `completed_no_candidate`다. 이 한도는 전체 법률 검색의 완전성을 뜻하지 않는다. 필터·페이지 관측을 지원하는 실제 어댑터가 구현되어야 해당 recipe를 사용 가능으로 등록한다.

정규화한 질의·필터·목적·앵커·자료군·정책 버전으로 `query_signature`를 만들고, 서버 실행 기록을 해당 단계에 연결한다. 수동 원자 조회도 같은 조건을 만족할 때만 인정한다. 모델이 만든 새로운 표현은 추가 탐색에 사용할 수 있지만, 지정된 필수 단계를 대체하려면 서버의 수락 규칙을 통과해야 한다. 반대 가설의 법률적 적절성까지 이 문자열 검사로 인증하지 않는다.

## 5. 출처의 권위와 후속 검토

### 5.1 출처 분류

`researchEvidence`에서 다음 관측 정보를 원문·제공자 응답과 함께 보존한다.

- 자료 종류, 발행기관, 법원·심급, 문서번호·사건번호, 선고일·발행일.
- 필드별 근거 위치와 관측 출처: 구조화 메타데이터 또는 원문 머리말.
- 서로 다른 출처가 충돌하는지, 해당 필드가 미확인인지.

공식 원천 정보에 근거한 서버 관측과 모델의 분류를 대조한다. 제공자의 `authorityLevel` 한 필드만 무조건 신뢰하지 않는다. 제목에 ‘대법원’이 있거나 예규 본문이 판결을 인용한다는 이유로 예규 전체를 대법원 판례로 승격하지 않는다.

명확한 불일치는 `AUTHORITY_KIND_MISMATCH`로 차단한다. 원문 정보가 부족하면 `AUTHORITY_IDENTITY_UNVERIFIED` 공백을 반환하고 추가 원문을 요구한다. 모델에게 종류를 다시 적게 하는 것만으로 공백을 해소하지 않는다.

### 5.2 후속 검토

`subsequent_review`를 다음 두 근거에 연결한다.

1. 그 문서·쟁점에 관해 실제로 실행한 후속 검색 기록.
2. 발견한 주요 후속 자료의 원문과 적용·구별·미해결 사유.

같은 예규 본문을 다시 인용한 것만으로 1번을 충족할 수 없다. 반대로 판결 자체에 원심·소송 경과가 적혀 있다면 그 부분은 해당 이력의 근거로 사용할 수 있다. 같은 문서 인용을 일괄 금지하지 않고, **후속 검색 이력과 원문 인용이 각각 입증하는 사실**을 구분한다.

검색에서 수집한 후보는 검토 원장에 남긴다. 주요 상위 판례·직접 관련 후보를 최종 답변의 인용 목록에서 빼더라도 원장에서 사라지지 않는다. 적용하거나 배제하려면 관련 법령 버전, 사실 차이, 원문 근거를 연결한다. 단순히 `irrelevant`라고 표시한 것만으로 핵심 후보를 닫지 않는다.

관련성·법리의 의미까지 결정론적 코드가 판정했다고 표시하지 않는다. 형식적으로 연결된 잘못된 배제 사유를 얼마나 잡는지는 실제 모델 평가와 독립 검토의 대상이다.

### 5.3 후보 신원·필수 처리·revision 수명 — Pro P1-2 반영

후보 목록은 서버가 검색 응답에서 추출한다. 식별 키는 `원천 이름공간 + 자료군 + 원천 문서 ID`이며, ID가 없으면 서버 후보 ID와 `identity_pending`을 남긴다. 원천 간 동일 문서라는 확인된 연결 없이 숫자 ID·제목만으로 합치지 않는다. 두 MCP가 같은 원천을 조회했다면 관측된 동일 키로 묶되 두 번의 발견 이력은 보존한다.

후보의 메타데이터 선별과 법률적 적용 판단을 분리한다. 다음은 첫 버전의 필수 처리 기준이다.

- 관측된 관련 조문이 앵커와 일치하는 법원 판례, 인용 중인 자료와 사건·후속 처리 관계가 확인된 후보, 모델이 근거로 채택한 후보는 원문 신원 확인과 적용 검토가 필수다. 대법원 여부는 처리 순서를 높이는 근거이지 낮은 심급의 관련 후보를 삭제하는 근거가 아니다.
- 앵커 검색으로 발견했으나 신원·조문 정보가 부족한 후보는 `triage_pending`이다. 메타데이터 상세 조회로 관련성을 좁힐 수 있지만 모델의 `non_major` 선언만으로 닫지 않는다. 애매하면 원문 검토 또는 명시적 미완료로 남긴다.
- 원문 조회 없이 닫을 수 있는 항목은 관측 신원이 같은 중복, 또는 서버가 확인한 명백한 검색 오분류다. 관련 조문이 적혀 있지 않다는 사실만으로 무관하다고 판단하지 않는다. 사실·법리 차이에 따른 배제는 원문과 이유를 갖춘 모델 판단으로 기록한다.

후보 A의 원문으로 연결한 receipt는 원천·자료군·문서 ID 및 관측 문서번호가 A와 일치해야 한다. 다르면 `CANDIDATE_DOCUMENT_MISMATCH`, 판별할 수 없으면 신원 공백이다. 본문 안에 A가 인용되어 있다는 이유로 다른 문서 B를 A의 원문으로 인정하지 않는다. 법적 적용 이유의 의미는 계속 미검증이다.

사실 보완·계획 변경 시 **후보 신원·최초 발견·과거 연결은 보존하고 현재 적용 판단과 검수 효력은 무효화**한다. 동일 앵커/쟁점의 후보는 `reassessment_required`로 다음 revision에 남긴다. 쟁점 ID만 바꾸거나 목록에서 삭제해도 과거 후보가 없어지지 않는다. 범위가 바뀐 항목은 `out_of_current_scope` 이력으로 남기고 원래 질문 범위가 해결됐다고 표시하지 않는다. 과거 발견은 새 검색 수행이나 새 조회 시각의 증거가 아니다. 세션 만료·재시작 이후까지 보존하는 영구 원장은 이번 범위에 넣지 않는다.

## 6. 이번 실패 사례의 사실관계 누락 방지

일시적 2주택 쟁점에는 별도 사건 프로필을 추가한다. 이 프로필은 결론 암기가 아니라 확인할 요건과 연혁을 제공한다.

- 전체 주택의 취득·처분 순서와 세대 기준의 보유 수 변화.
- 신규주택 취득 직전 보유 수와 그 산정 근거.
- 종전주택·신규주택의 취득, 다른 주택 처분, 종전주택 양도의 날짜 역할.
- 상속·혼인 등 별도 특례 가능성을 확인할 사실.
- 각 요건이 어느 시점에 충족되어야 하는지와 그 법령·판례 근거.

‘최종 양도 시점에 두 채’라는 사실만 등록하여 전체 연혁을 대신할 수 없게 한다. 이미 확인한 진술은 재사용하고, 월 단위 날짜를 임의의 일자로 바꾸지 않는다. 빠진 사실은 결론에 중요한 순서로 최소한만 묻는다.

해당 프로필을 사용하지 않은 세법 사건에도 공통 판례 조회 의무는 적용한다. 프로필 선택을 누락하면 모든 사건 요건을 자동으로 발견할 수 있다는 주장은 하지 않는다. 프로필 누락·잘못된 쟁점 등록은 별도 모델 평가에 포함하고, 등록 범위 밖의 완전성을 보증하지 않는다.

대표 회귀 입력은 ‘종전주택 2016년 취득 → 신규주택 2026년 2월 취득 → 다른 일반 주택 2026년 4월 처분 → 종전주택 2026년 12월 양도 예정’으로 비식별화한다. 판례번호를 사용자 입력에 넣지 않은 상태에서 조사하게 한다.

`2024두55426`과 관련 예규는 이 회귀의 조사 후보로 사용한다. 구현 시 공식 판결 원문·사건 적용 법령·부칙을 다시 대조하여 고정한다. 이 계획은 해당 거래의 비과세 여부를 새로 확정하지 않는다. 기대 동작은 **직접 관련 상위 근거를 찾고 법령·사실과 대조하기 전 예규만으로 확정 결론을 내리지 않는 것**이다.

## 7. 도구 흐름과 데이터 계약

다음 명칭·필드는 구현 제안이며 현재 제공되는 API라고 안내하지 않는다.

### 7.1 도구 흐름

1. `start_legal_research`: 기존 계획을 받고 서버 정책으로 자료군별 조회 의무와 필요한 사실 확인을 반환한다.
2. 신규 `run_required_legal_research`: 미완료 조회 의무를 정해진 예산 안에서 실행한다. 조사 범위와 다음 작업 위치를 반환하여 이어서 수행할 수 있게 한다.
3. 기존 `research_legal_sources`: 후보 원문 조회와 추가 검색에 계속 사용한다. 동일한 서버 기록 형식에 연결한다.
4. `review_legal_reasoning`: 기존 인용·사실·시점 검사에 자료군 검색, 출처 분류, 후속 검토 검사를 추가한다.
5. `get_legal_research`: 검수 여부, 수행한 검색, 해결되지 않은 공백, 남은 예산을 확인한다.

모델이 새 실행 도구를 생략해도 4번의 검사에서 누락이 드러나야 한다. 기존 원자적 조회 도구로 동일 의무를 충족하는 것은 허용하되, 서버가 실제 호출 범위와 결과를 보고 연결한다. 클라이언트가 올린 ‘검색 완료’ JSON은 조회 기록으로 인정하지 않는다.

### 7.2 저장할 정보

| 객체 | 핵심 필드 |
| --- | --- |
| 조회 의무 | `obligation_id`, 쟁점 ID, 정책 버전, 자료군, 조사 목적, 필요한 검색 범위, 현재 상태 |
| 검색 기록 | 세션·revision·의무 ID, 도구·제공자·원천, 정규화한 검색어·필터, 요청/응답 해시, 시각, 결과 상태, 후보 ID, 페이지 범위 |
| 출처 관측 | 원문 식별자, 종류·기관·심급, 선고/발행일, 필드별 근거, 불일치·미확인 상태 |
| 후보 처리 | 발견 검색 ID, 원문 receipt, 적용/구별/미해결, 법령 버전·사실 연결, 이유 |
| 검수 결과 | 기존 해시 결합, 자료군별 완료 상태, 출처 분류 공백, 후속 검토 공백, 다음 조회 작업 |

현재 `arguments_hash`만 저장하는 방식으로는 어떤 법원·기간·검색어를 조사했는지 대조할 수 없다. 필요한 정규화 필드를 제한된 크기로 추가하되 개인정보·공개 세션 토큰·원문 전체를 운영 로그에 출력하지 않는다.

조문·사건일·핵심 사실·검색 정책이 바뀌면 관련 검수는 무효화한다. 다른 세션, 과거 revision, 다른 조사 범위의 성공 기록을 그대로 재사용하여 완료 처리하지 않는다.

재시도 성공 시 실패 기록을 삭제하지 않는다. **같은 조회 의무와 같은 범위를 충족한 대체 성공 기록**이 있을 때만 해당 실행 공백을 해소한다. 다른 날짜·필터·쟁점의 성공, 또는 여전히 부분인 본문은 대체 성공이 아니다. `researchReview`와 `scopeCompletion`에 같은 해결 규칙을 적용한다.

### 7.3 공통 유효 상태 계산 — Pro P1-3 반영

`researchCoverage`의 단일 계산 결과를 `researchReview`, `legalApplicability`, `scopeCompletion`이 소비한다. 검색 실행 기록은 문서 receipt와 별도 자료형으로 둔다. `purpose=counter`인 검색 결과를 반대 문서로 세거나 그 검색 목록 자체에 판결 본문을 요구하지 않는다.

| 현재 관측 | 조회 의무 | 문서·후속 검토와 전체 완료 |
| --- | --- | --- |
| 현재 revision의 필수 단계 미실행·오류·범위 불명 | 미완료 | 조건부/유보는 공백·다음 작업을 표시, 확정 결론은 차단 |
| 현재 recipe의 정상 반대 검색이 0건 | 검색 수행 완료 | 반대 문서 개수·가짜 인용을 요구하지 않음. 다른 법령·사실·후속 의무는 계속 검사 |
| 특정 authority의 정상 후속 검색이 0건 | 해당 후속 검색 완료 | `search_attempt_ids`로 수행 확인, 빈 후속 후보 집합이면 `subsequent_review.citations`를 강제로 채우지 않음 |
| 후보가 발견됨 | 검색 수행은 완료 가능 | 필수 후보의 신원·원문·적용/구별 처리가 끝나기 전 전체 검수는 미완료 |
| 같은 revision·의무·범위의 대체 성공 | 해당 실행 공백만 해소 | 실패를 삭제하지 않고 `resolved_by_attempt_id` 연결을 서버가 검증 |
| 과거 revision의 성공/실패 | 현재 수행 증거로 세지 않음 | 감사 이력으로 유지. 과거 실패만으로 현재 scope를 영구 차단하지 않음. 후보는 §5.3에 따라 재검토 |
| 부분 본문을 같은 신원·버전의 완전 본문으로 대체 | 그 원문 확보 공백만 해소 | 인용이 새 receipt로 옮겨졌는지 별도 검사. 여전히 이전 부분 본문을 인용하면 통과하지 않음 |

`subsequent_review`에는 검색 ID와 발견 후보 처리를 추가하고 문서 인용은 실제 발견한 후속 원문에만 요구한다. 본문이 입증하는 과거 소송 경과와 조회일 현재의 후속 검색 의무는 별도다. 새로운 후속 자료가 핵심 적용 근거가 되면 그 자료에도 후속 검토를 연결하되, 동일 문서/동일 검색 범위의 순환은 중복 작업으로 처리한다. 조사 한도에서 끝내지 못하면 미완료이며 무한 재귀나 가짜 자기 인용으로 종료하지 않는다.

판정 단위는 `세션 + revision + 정책 + 의무 ID + 필수 단계 + 수락된 범위`다. 부분 범위의 성공이 전체 실패를 해결하지 않는다. 여러 단계가 합쳐 범위를 충족하는 경우에도 각 필수 단계가 따로 검증되어야 한다. 계획 변경 후에는 현재 의무를 새로 평가하며, 과거 원문 재사용을 허용하더라도 현재 revision에 대한 새 신원·적용 연결이 필요하다. 보관된 원문을 다시 연결한 행위는 외부 재조회로 표시하지 않는다.

AC-28에는 단일 전체 응답을 나눈 정상 사례와 원천이 보장한 불변 snapshot의 부분 조회를 합친 정상 사례도 포함한다. 발행일·`unknown`·로컬 조립 해시만 같은 응답은 전체 원문의 동일성을 입증하지 못한다. AC-29는 31개 저장 단위가 있는 상태에서 2개가 필요한 응답, 남은 바이트 초과, manifest 최종 반영 실패를 각각 주입한다. 모두 새 분할 묶음이 노출되지 않고 명시적 용량 실패로 종료되며, 응답 유실 뒤 같은 요청의 재전송은 재조회 없이 그 실패를 반환해야 한다. 정상 다중 단위의 일괄 반영, 원천 응답 수신 한도 초과, 만료/구 revision의 지연 응답과 정리 작업이 새 작업의 예약·busy를 해제하지 않는 경우도 검사한다.

기존 `AP-01`의 ‘예규만으로 구조 완료’ 기대값은 새 정책에 맞게 바꾼다. 의미 없는 판례 fixture 한 건을 추가하여 기존 성공 조건만 복원하지 않는다. 의무 생성·조회 수행·범위 대조·완료 판정 각각을 검증한다.

범위 밖 요청, 과도한 검색, 정상 답변을 불필요하게 차단하는 경우도 실패로 기록한다. 차단율이 높아졌다는 이유만으로 품질 개선을 주장하지 않는다.

## 10. 실제 검색과 모델 평가

결정론적 테스트, 제공자 통합 확인, 실제 모델 행동을 별도 결과로 남긴다.

1. **합성 회귀:** AC-01~31, 기존 인터뷰·scope·MCP/REST·공개 접근·PR 경계 검사.
2. **실제 검색:** 판례번호를 넣지 않은 쟁점 검색에서 대표 판결을 후보로 찾는지, 원문과 출처 분류가 확보되는지 확인. 실제 원천 오류와 모델 검색 선택 오류를 구분.
3. **모델 실행:** 제보 모델·설정을 확인할 수 있는 클라이언트에서 아래 8개 시나리오를 각 3회 실행하는 24회 파일럿. 실행 가능한 실제 모델 ID·클라이언트·시각·도구 호출을 기록하며 모델 이름을 추정하지 않는다.

| 시나리오 | 관측 목표 |
| --- | --- |
| 다주택 처분 후 마지막 2주택 | 판례번호 힌트 없이 신규주택 취득 전 상태·판례 검색·상충 근거 검토 수행 |
| 대응하는 일반 1주택 → 일시적 2주택 | 다른 사실관계의 불리한 판례를 기계적으로 적용하지 않음 |
| 대법원 판결 후 법령 개정 | 개정 전후 사건을 나누고 구법 판례를 무조건 폐기하거나 무조건 적용하지 않음 |
| 행정해석만 발견되는 쟁점 | 정상 0건을 설명하고 없는 판례·반례를 만들어내지 않음 |
| 첫 제공자 장애 | 실패를 기록하고 대체 경로 또는 조건부 답변으로 처리 |
| 오래된 예규와 후속 변경 자료 | 자기 인용만으로 후속 검토를 끝내지 않음 |
| 조문 내용만 묻는 질문 | 사건 인터뷰·전체 판례 조사를 강요하지 않음 |
| 연구 도구 없이 일반 조회만 이용하려는 흐름 | 검수 미실행을 드러내고 검수됐다고 주장하지 않음 |

정답표·기대 판례번호는 모델 입력에서 제외한다. 문서번호 직접 조회만 성공한 결과를 판례 발견 성공으로 집계하지 않는다. 대표 실패의 검색 발견율, 필수 도구 실행률, 미완료 상태의 확정 답변, 부당한 차단, 질문 반복, 호출 수·지연을 함께 보고한다.

24회는 파일럿이며 정확도의 통계적 보증이 아니다. 실제 법률 결론의 기대값은 적용 법령·판결 원문에 근거해 별도로 검토한다. 서버 게이트는 통과했으나 모델이 잘못된 법리를 선택한 경우도 별도 실패로 남긴다.

다른 공급자의 MCP 클라이언트에서도 최소 연결·조회·검수 흐름을 확인한다. 실행하지 못한 클라이언트는 미검증으로 표시하며, 모든 모델에서 검수 호출이 강제된다고 안내하지 않는다.

### 10.1 파일럿 출시 판정표 — Pro P1-5 반영

아래 합격선과 각 시나리오의 기대 동작·평가 입력·판정자를 첫 실행 전에 고정한다. 실행 뒤 어려운 사례나 장애 건을 분모에서 빼지 않는다. 법률 결론의 정답표는 원문 검토를 거쳐 평가자에게만 제공하고 모델 입력에 누출하지 않는다.

| 판단 대상 | 합격 기준 | 실패·미실행 처리 |
| --- | --- | --- |
| 서버 계약 | AC-01~31과 기존 필수 검사가 모두 통과. 누락·신원 위조·후보 바꿔치기·범위 세탁의 완료 승격 0건 | 한 건이라도 있으면 구현 수정 전 출시 불가 |
| 대표 실패와 정상 대조 | 각 3회 모두 번호 힌트 없이 필요한 근거 발견·원문 확보·적용/구별 검토. 완전한 사실을 제공한 정상 대조는 부당한 차단 없이 완료 | 전부 유보하거나 문서번호 직접조회만 성공하면 불합격 |
| 0건·개정·후속 자료 | 각 3회 모두 사전 기대 절차/상태 충족. 없는 자료 생성·구법 판결 일괄 배제·후속 자기 인용 대체 0건 | 검색 안전성과 법리 선택 오류를 따로 기록하고 해당 실패 수정 |
| 장애 주입·일반 조회 | 각 3회 모두 장애 시 기대한 재시도/조건부 상태, 일반 조회 시 불필요한 인터뷰 없이 자료 반환 | 장애 시 조건부 처리는 정상 경로. 정상 검색도 실패한 결과로 이를 대신하지 않음 |
| 모델·클라이언트 조합 | 24회 전체에서 관측된 미완료를 숨기거나 검수 완료로 바꾼 발언 0건. 필요한 연구·검수 절차를 각 시나리오에서 수행 | 해당 조합에 대한 개선 확인·지원 주장은 보류. 서버 통과와 혼합 집계하지 않음 |
| 평가 누락·대체 모델 | 실제 모델 ID/설정·클라이언트·원천 상태를 기록하고 필수 실행을 완료 | 미실행은 미검증. 원 모델 확인이 불가능하면 식별 가능한 대체 조합의 결과만 명시하며 원 사건의 원인 규명으로 주장하지 않음 |

대표 입력의 월 단위 날짜는 그대로 유지한다. 검색 발견 여부와 날짜 정밀도 공백을 별개로 채점한다. 정상 완료를 검증하는 대조 실행에는 평가자가 사전에 만든 **별도의 합성·완전 사실 패킷**을 제공한다. 모델이 실제 사용자 날짜를 임의로 보충해서 통과한 결과는 실패다. 원문 미확보 등 실제 서비스 장애도 전체 실행 결과에 남기며, 필요한 정상 조회가 검증되지 않았다면 그 부분을 통과로 기록하지 않는다.

24회는 소규모 운영상 통과 기준이다. 통계적 정확도 보증이나 모든 모델 지원 선언으로 사용하지 않는다. 기준에 실패한 조합의 지원 범위를 조용히 줄여 전체 목표 완료로 표시하지 않으며, 어떤 검증이 남았는지 기록한다. 호출·지연·RSS 측정과 예산 내 정상 완료도 §11의 별도 출시 조건이다.

## 11. 자원·사용성·운영 제약

- 첫 구현은 기존 메모리 세션을 재사용한다. 새 DB·서버·유료 크롤링 계약을 필수 구성으로 추가하지 않는다.
- 현재 세션의 30분 TTL, 40회 시도·32개 증거·1MiB와 전체 용량 제한을 고려하여 기록을 제한한다. 한도를 넘기면 남은 작업을 표시하고 완료로 바꾸지 않는다.
- 새 실행 도구 한 번으로 내부 호출 여러 건을 무료 처리하지 않는다. 모든 하위 원천 호출에 기존 조회 예산과 동시 작업 보호를 적용한다.
- 응답 제한 시간 안에 끝낼 수 있는 단위로 분할하고 재개 위치를 반환한다. 클라이언트 응답 유실·재전송에 따른 중복 조회와 살아 있는 작업의 중복 실행을 시험한다.
- 실패 재시도는 횟수·전체 시간·남은 예산으로 제한한다. 0건에 대한 검색어 보완과 오류 재시도를 구별한다.
- 동일 원문은 세션 안에서 재사용할 수 있으나 새 조회 시각·새로운 적용 확인으로 위장하지 않는다. 결과의 출처 시각과 캐시 여부를 표시한다.
- 정상 조회와 사건 판단의 호출 수·지연·RSS·timeout을 변경 전후에 측정한다. 기존 동시 작업 한도에서 OOM·작업 누수·일반 조회 기아가 없는지 확인한다.
- 대규모 다쟁점 검토가 예산을 소진하면 범위별 미완료를 표시한다. 조사 범위를 조용히 줄이거나 쟁점을 지워서 통과시키지 않는다.

### 11.1 저장·호출 예산과 재개 계약 — Pro P1-4 반영

첫 버전의 상한은 기존 30분 TTL·40회 원천 호출 시도·32개 인용 원문 저장 단위·세션 1MiB·전체 8MiB를 유지한다. 세션 1MiB에는 보관 상태와 최종 저장 예약을 포함하고, 아래의 별도 임시 수신 공간도 전체 8MiB에는 합산한다. 다음은 그 안의 **설계 배분안이며 아직 실측 결과가 아니다.** 구현 시 직렬화한 UTF-8 바이트와 활성 예약량을 포함해 입장 검사를 한다.

| 저장 종류 | 초기 상한과 처리 |
| --- | --- |
| 검색·후보·작업 메타데이터 | 합계 256KiB 이하, 검색 시도 최대 40개·서버 후보 최대 128개. 검색 목록은 32개 원문 한도를 소비하지 않음. 초과 후보는 조용히 버리지 않고 `candidate_overflow` 범위를 남김 |
| 인용 원문 저장 단위 | 합계 640KiB 이하에 진행 중 예약 포함, 단위당 128KiB 이하·최대 32개. 직렬화한 바이트와 필요한 단위 수를 함께 예약하며 manifest·종료 상태의 별도 공간도 확인 |
| 계획·인덱스·기타 상태 | 128KiB 이하. 최종 합계 1MiB 검사를 별도로 적용. 이력은 용량 때문에 임의 삭제하지 않음 |

**원문 snapshot 결속 — R-1.** 법령의 적용 버전·시행일, 판결의 선고일·문서 발행일과 **조회한 원문 자체의 불변 snapshot 식별자**를 별개로 저장한다. 현 어댑터의 `document_version` 날짜나 `unknown`은 snapshot 보장으로 사용하지 않는다. 큰 원문은 다음 두 경로만 허용한다.

- (a) 서버가 한 번에 받은 절단되지 않은 전체 응답의 불변 바이트를 기준으로 분할한다. 모든 조각을 그 단일 응답 ID·응답 해시·문서 신원에 결속하고, 필드별 원래 범위와 해시를 보존한다. 이는 받은 응답 안의 일관성을 입증하며 원천의 최신성이나 법률적 정확성을 추가로 인증하지 않는다.
- (b) 여러 부분/조문 응답을 합치려면 제공자가 보장하는 불변 snapshot ID, **문서 전체 표현에 적용되는 강한 validator**, 또는 조각들과 별도로 확보·검증한 원천의 전체 해시/manifest가 필요하다. 어댑터는 그 보장과 부분 응답의 결속을 검증해야 한다. 부분 응답별 ETag, 같은 ID·발행일·길이, 약한 validator, 로컬에서 만든 조립 해시만으로는 충분하지 않다. 동일 snapshot의 전체 범위가 확정되고 누락·겹침·해시 불일치 없이 모두 확보되어야 완전 확보로 처리한다.

문서 manifest에는 문서 신원·법적 버전과 별도의 snapshot 근거·필드별 전체 길이/범위·해시·분할 경로를 기록한다. 원천부터 잘린 자료를 나누거나 snapshot이 다른 부분 응답을 합쳐 `body_returned`로 승격하지 않는다. (b)의 보장을 제공하지 않는 어댑터는 이 경로를 완료 가능으로 등록하지 않고 (a) 또는 다른 원천을 사용한다. 전체도 예산에 들어가지 않으면 명시적 공백을 유지한다. 원문이 바뀌거나 불완전하다고 같은 부분을 무한 재조회하지 않는다.

**분할 저장의 예약·반영·종료 — R-2.** 한 응답이 여러 저장 단위를 만드는 경우에도 다음 절차를 지킨다. 현재의 단일 receipt 예약을 그대로 재사용하지 않는다.

1. 원천 호출 전에 작업 ID·소유 토큰에 묶인 단계와 **상한이 정해진 종료 상태 레코드·공백 표시 공간**을 메타데이터 예산에 예약한다. 이후 용량 실패를 기록할 공간까지 있어야 작업을 수락한다. 이를 확보하지 못하면 원천 호출 없이 입장을 거절하고 `pending` 작업을 만들지 않는다. 이미 수락한 작업의 종료 기록은 새 용량 확보에 의존하지 않는다.
2. 응답 크기를 모를 때는 최종 저장 예약과 별도로 **호출당 최대 4MiB의 임시 수신·분할 준비 공간**을 상한으로 예약한다. 실제 허용량은 그 상한과 남은 전체 예산 중 작은 값이며, 기존 저장·활성 예약·임시 공간의 합계를 전체 8MiB 안에서 관리한다. 전체 응답을 무제한으로 읽거나 파싱한 뒤 크기를 검사하지 않는다. 어댑터/전송 계층에서 수신 한도를 적용하고 초과 시 중단·실패 처리한다. 이 수치는 직렬화 데이터 예산이며 JavaScript 힙/RSS 상한 보증이 아니므로 §11의 RSS 실측은 별도로 필요하다.
3. 관측 응답에서 필요한 **저장 바이트·저장 단위 수·manifest·성공/실패 단계 상태**의 비용을 계산한다. 임시 데이터와 반영 준비 데이터가 동시에 존재하는 비용도 포함해 모든 세션/전체 한도에 대한 최종 예약을 원자적으로 확보한 뒤 반영한다. 바이트만 남았거나 32개 한도에 한 칸만 남았는데 두 조각이 필요하면 실패다. manifest는 메타데이터 예산에 포함하며 어느 한도에서도 예외 공간을 만들지 않는다.
4. 같은 actor·세션·revision·작업 소유 토큰이 여전히 유효할 때 **새 조각 묶음 + manifest + 단계 결과 + 예약 전환/해제 + busy 해제**를 단일 상태 변경으로 반영한다. 조각 하나씩 공개한 뒤 나머지를 저장하지 않는다. 부분 조회를 여러 단계로 나누는 경로에서는 각 단계의 새 묶음만 원자적으로 반영하며, 전체 범위가 닫히기 전 manifest는 계속 `partial`이다. 기존 완전 manifest와 새 불완전 snapshot을 혼합하지 않는다.
5. 용량·직렬화·manifest 반영 실패 시 **이번 단계의 미반영 조각을 전부 폐기**하고 기존 후보·조회 이력·이미 반영된 부분 자료를 유지한다. 미완료 공백과 `failed` 종료 상태 및 제한된 오류 코드를 사전 예약 공간에 기록하고, 해당 작업의 임시/최종 예약과 busy를 함께 해제한다. 실패 저장 자체가 새 용량을 요구하거나 처리 가능한 예외 뒤 영구 `pending`이 남아서는 안 된다. 같은 요청의 재전송은 저장한 이 실패를 반환하며 자동 재조회하지 않는다.
6. 성공 반영과 실패 정리는 모두 같은 revision/소유 토큰 검사 아래 수행한다. revision 교체·만료·종료 시 중앙 상태 전이가 그 revision 작업을 폐기하고 해당 작업이 가진 예약만 반환한다. 뒤늦은 콜백은 새 revision의 결과·예약·busy를 변경하거나 만료 세션을 되살릴 수 없다. 세션이 사라졌다면 기존 작업의 만료/무효를 반환하며 영구 실패 기록이 보존됐다고 주장하지 않는다. 프로세스 재시작에 따른 메모리 유실은 아래 TTL 계약을 따른다.

정상 단일 쟁점의 초기 호출 예산 목표는 아래와 같다. 모든 수치는 설계 목표다. AC-30에서 실제 어댑터·한 차례 사실 보완·대표 원문 크기로 측정한 호출 수와 바이트를 별도 증거에 채워야 하며, 표를 작성한 것만으로 운영 검증을 통과하지 않는다.

| 핵심 자료의 후속/개정 조회 | 4 |
| 사실 1회 보완 뒤 영향 범위 재조회·명시적 실패 재시도 | 8 |
| 합계 / 전체 한도까지 여유 | 30 / 10 |

반복 인터뷰는 조사 전에 우선 해결하되 초기 원문 조회가 필요한 질문은 허용한다. 사실 보완 뒤 기존 원문 내용은 같은 세션의 제한된 캐시로 재연결할 수 있지만 검수·적용 관계는 다시 계산한다. 외부 호출을 하지 않았다면 새 조회 시각이나 새 검색 성공을 만들지 않는다. 여러 쟁점이 한도를 초과하는 경우까지 이 표가 정상 완료를 보장하지 않는다.

`run_required_legal_research`는 한 번에 최대 4개의 관측 가능한 원자 단계를 처리하고, 현재 외부 응답 제한보다 이른 시간에 재개 위치를 반환한다. 단계의 원천 호출마다 예산을 소비한다. 복합 제공자의 내부 호출은 하위 실행 기록이 없으면 이 수치에 포함됐다고 주장하지 않는다. 필수 검색 실행은 원자 도구를 우선 사용하며, 실제 upstream 내부 자원 보호는 제공자 쪽 동시성 제한도 유지한다.

재개 프로토콜은 다음으로 고정한다.

1. 요청의 `request_id`는 중복 방지용일 뿐 완료 증거가 아니다. 서버가 actor·세션·revision·정책·정규화 인수에 묶어 작업 ID를 발급하고, 원천 호출 전에 단계와 용량을 예약한다. 같은 요청 ID에 다른 인수를 보내면 거절한다.
2. 각 단계는 의무 ID·단계 ID·질의 signature와 서버 작업 소유 토큰에 묶인다. 완료 결과를 저장한 뒤 응답한다. 응답 유실 후 같은 요청을 보내면 보관한 결과/재개 위치를 돌려주고 조회를 다시 하지 않는다.
3. 아직 실행 중이면 같은 작업의 `pending` 상태만 반환한다. 대기 시간이 지났다는 이유로 같은 조회를 동시에 시작하지 않는다. 실제 실패가 확정된 단계만 제한된 별도 재시도로 예약하고 그 연결을 보존한다.
4. revision 변경·만료·종료가 발생하면 과거 작업 토큰은 현재 상태에 쓸 수 없다. 지연된 응답도 만료 세션을 되살리지 않는다. 상태를 바꾸는 작업과 검수는 기존 원자적 `busy`/revision 검사를 유지한다.
5. TTL은 재개로 연장하지 않는다. 만료·서버 재시작 후에는 메모리 작업을 이어갈 수 없다고 반환한다. 기존 작업 ID를 새 세션에 제출해도 새 성공 기록으로 받아들이지 않는다.

추가 메타데이터·원문 manifest·후보 이력·작업 상태는 모두 검수 snapshot 해시에 포함한다. 정상적인 한 차례 사실 보완 후 완료할 수 있는지, 큰 원문이 항상 잘려 실패하는 경로만 남지 않았는지를 실제 설치 패키지에서도 확인한다.

## 12. 호환성·검수·배포

### 호환성

정책 버전과 응답의 관측 필드를 추가하고 MCP·REST·Actions 스키마를 함께 갱신한다. 새 필드가 없는 기존 연구 입력은 가능한 한 구조 오류 대신 명시적 검수 공백으로 처리한다. 확정 결론은 누락 상태에서 통과시키지 않는다. 일반 조회 도구의 입력 형식은 유지한다.

정책 전환 전 세션이나 이전 결과를 새 정책 통과로 표시하지 않는다. 기존 재시작 시 세션 소멸 계약을 안내하고, 같은 프로세스에서 정책이 바뀌는 경우에도 이전 검수 해시를 무효화한다.

### 단계별 독립 검수

| 검수 단계 | 검수 자료 | 확인할 사항 |

Pro가 실제로 응답하기 전에는 검수 완료로 기록하지 않는다. 구현이 바뀌면 영향받는 검사와 검수 증거만 갱신한다. 일반 사건마다 독립 서버 AI를 자동 호출하는 기능과 패치의 독립 검수는 구분한다.

### 배포

관련 표적 검사 후 `npm run review`, `npm run review:package`와 CI 필수 검사를 수행한다. 설치된 패키지에서도 새 조회 기록과 완료 판정을 확인한다.

최종 PR을 사람이 검수·병합하면 [기존 main 자동 배포](AUTO_DEPLOY.md)가 동작한다. 계획 문서 작성은 머지·배포 실행을 뜻하지 않는다. 별도의 자동 머지 경로를 만들지 않는다.

운영에서는 릴리스 SHA·정책 버전, 공개 MCP 도구 목록, 일반 조문 조회, 판례 검색이 빠진 검수의 차단, 정상 검색·검수 흐름을 확인한다. health 200이나 도구 목록 노출만으로 완료하지 않는다.

공개 조회 장애·세션 격리 회귀·과도한 호출·핵심 정상 사례 차단이 발생하면 기존 검증된 릴리스로 복구한다. 이전 정책으로 복구된 경우 강화된 검사도 되돌아갔음을 표시하고, 새 정책 통과 결과를 계속 유효하다고 제공하지 않는다.

## 14. 실측 후 구현 계약 보완 — 2026-10-01 Pro F-1~6

중간 Pro 검수 원문은 `reviews/AUTHORITY_COVERAGE_IMPLEMENTATION_PRO_RESPONSE_2026-10-01.txt`에 보관한다. 이 절은 §4.3·5.3·11.1의 구체화를 보완하며 §10.1의 출시 합격선은 낮추지 않는다. 기존 계획 승인과 아래 변경의 구현·출시 승인은 별개다.

1. 필수 검색은 사전에 생성한 `criterion-v2` recipe로 실행한다. 일시적 2주택 취득 순서 쟁점은 관측된 법령명·조문에 `신규 주택`과 별도 `신규 주택 3주택` 검색 축을 적용하고 공식 대법원 필터를 검증한다. NTS는 `일시적 2주택 비과세 취득 선후`와 관측 조문을 결합해 법원·해석·심판·심사를 각각 조회한다. 정답·사건번호를 검색식에 넣지 않는다. 다른 쟁점은 공통 앵커 recipe를 적용하며 미완료 범위는 그대로 표시한다.
2. 필수 recipe 밖의 수동 검색은 실행 전에 보조 탐색으로 기록한다. 실패 후 필수 기록을 보조로 변경하지 않는다. 보조 검색의 partial·실패·후보는 원장과 `exploratory_gaps`에 남지만 조문 전체 전수조사가 필수 범위에 자동 편입되지는 않는다. 필수 검색에서도 발견되거나 근거로 채택된 자료는 이 경로로 제외할 수 없다.
3. 필수 검색으로 발견한 후보는 여전히 원문·적용 검토를 요구한다. 모델의 non_major 선언이나 상위 N건 자르기는 없다. 대법원·법령 버전 원문을 먼저 읽는다. 후속 검색으로 추가 발견한 자료도 원문과 구별 이유를 읽지만, 구별된 보조 후속 자료에서 다시 무한 후속 검색을 만들지 않는다. 이를 채택·유추하거나 직접 주장에 사용하면 후속 의무가 추가된다. 검수에서 반환한 `next_step`은 실제 조회 도구로 수행할 수 있다.
4. 심판은 심판 후속, 심사는 심사 후속, 각각 관련 법원 사건을 별도 확인한다. 자료 종류를 관측할 수 없으면 공백이다. 법원 0건으로 심판·심사 확인을 대신하지 않는다. 법령 검색의 법령ID/MST/시행일은 버전 후보로 등록하며 정확한 MST 원문과 `legal_basis.statutes`·`temporal_application` 대조가 필요하다. 원문 인용의 법률적 의미까지 자동 인증하지 않는다.
5. 대체 원문 성공은 기록된 문서 신원·문서번호·알려진 버전·날짜 역할·쟁점·목적이 일치하고 필요한 전체 반환 본문을 확보했을 때만 이전 실패를 해결한다. 다른 도구명이라는 이유만으로 거부하지 않으며 다른 문서·다른 시점·부분 본문은 대체가 아니다.
6. `reuse_legal_evidence`는 세션에 이미 있는 완전한 manifest 전체를 현재 revision의 쟁점에 재연결한다. 불변 바이트·최초 관측 시각·원본 revision은 유지한다. 검색을 새로 했다고 표시하거나 이전 법률 판단·검수 효력을 복원하지 않는다. 세션 밖 캐시, 불완전한 분할 묶음, 임의 업로드는 허용하지 않는다.
7. 기관·법원 필드는 독립적으로 관측한다. 확정 권위가 충돌하면 conflict이고 한 필드가 없을 때 다른 명확한 필드를 사용할 수 있다. 본문 인용이나 authorityLevel 하나로 권위를 올리지 않는다.
8. 진행 중 수신 예약은 세션 Map과 별도의 작업 토큰 Map에서 관리한다. 세션 TTL/close 이후에도 실제 호출·수신·정리가 끝나기 전에는 전체 메모리 회계에서 빼지 않는다. 만료 세션이 붙잡고 있는 저장 상태도 계산한다. 새 작업이나 세션은 오래된 정리 콜백으로 영향을 받지 않는다.
9. 실제 모델 평가에서 확인한 복구 경로를 반영한다. 검수에서 후속 발견 자료를 새 근거로 채택하면 해당 의무를 세션 snapshot·state_version과 다음 자동 조회에도 반영한다. 중립 검색에서 발견한 본문을 반대 근거로 평가할 수 있지만, 원문·쟁점 귀속·반론 해결 인용 및 별도 반대 검색 의무는 그대로 검사한다.
10. 동일한 관측 법령명·조문을 공유하는 관련 쟁점은 사건의 검색 맥락을 유지한다. 별도 법령의 쟁점에는 맥락을 전파하지 않는다. 조문 앵커·자료군·채널·검색 목적·실제 도구와 인수가 모두 같은 사전 생성 의무에 한해서 한 번의 관측 조회를 함께 사용한다. 자료군, 반대 검색, 페이지, 개정 검색을 서로 대체하지 않는다.
11. 4단계 배치 완료와 전체 자료 확보를 구분해 남은 검색·미확보 본문·적용 검토 목록을 응답 앞에 표시한다. 선택한 evidence_id의 원문만 다시 읽을 수 있으며 나머지 저장 원문이나 검수 상태를 삭제하지 않는다. 입력 오류에는 허용값·타입·범위를 안내하되 사용자 입력값이나 임의 진단문을 반사하지 않는다. 실제 다른 주택의 처분 없이 단순히 “다른 주택 없이”라는 문구만으로 처분일을 요구하지 않는다.

실측 개발 검증에서는 같은 취득 순서 recipe가 외부 원자 호출 38회, 저장 단위 15개, 후보 14개로 종료됐다. 이는 검색·반환 원문 단계의 관측이며 법률 적용 검수·24회 모델 파일럿 통과를 뜻하지 않는다. 소스 내부의 HTTP 호출 수는 미관측이다. 최초 급속 실행에서 원천 RATE_LIMITED가 발생했으며 오류를 0건으로 바꾸지 않았고 후속 실행은 원천 한도를 존중해 간격을 두었다. 모든 실제 모델 평가에 같은 한도와 판정 기준을 적용한다.

## 15. 최종 모델 평가 후 보완 계획

최종 `pilot-i`는 22건 의미 검수 통과·2건 실패였으며 출시하지 않았다. 후속 조사에서 같은 revision의 원문 재사용이 기존 쟁점 귀속을 덮어써 검색을 확대하는 경로를 확인했다. 재사용 귀속·복구 응답·필수 요건의 근거 연결과 검증 계약은 [완료 경로 보완 계획](AUTHORITY_COVERAGE_COMPLETION_FIX_PLAN.md)에 분리했다. 이 문서 추가는 해당 수정의 구현이나 별도 Pro 승인, §10.1 출시 합격선 변경을 의미하지 않는다.
