# 정상 검색 0건과 조회 실패 구분 계획

원래 계획 작성일: 2026-11-07 KST. 구현 현황과 실제 검수·배포 결과는 별도 실행 기록을 참조한다.

목표는 정상적으로 끝난 빈 검색을 오류 없이 반환하면서, 자료가 있는데 못 읽거나 응답을 해석하지 못한 경우를 정확히 드러내는 것이다. `NOT_FOUND`라는 이름만 바꾸지 않고, 원본 응답을 검증한 자료 공급 도구가 판정 근거를 전달하도록 한다.

이 계획은 [개발용 측정 계획](DEVELOPER_MEASUREMENT_PLAN_20261104.md)과 별도의 기능 수정 단위다. 측정만으로 조회 결과를 바꾸지 않는 원칙은 유지한다. 이 계획에서 의도적으로 바뀌는 동작은 **검증된 목록 검색 0건의 응답 상태와 그에 따른 분류**다. Pro 검수 전에 구현하지 않는다.

## 1. 확인한 소스와 한계

검토 기준 harness는 `1e6aa272c8fb24097d67fdf83c7e5d6eade3dd37`이다. 해당 커밋의 기존 Node 22 검증은 [455개 통과 및 패키지 10개 검사 통과](https://github.com/hyunae52/legal_harness/actions/runs/42304197143)다. 이 결과는 현재 기능의 기준선이며, 아래 새 동작을 검증한 결과가 아니다.

- 국세 공급 도구는 `search_documents` 결과의 `items`가 비어 있으면 `NOT_FOUND`를 만든다. [고정 버전 server.py](https://github.com/hyunae52/korean-taxlaw-mcp/blob/16a08b9af70f49fc60a5f54ab0f9812be206c8f5/src/korean_taxlaw_mcp/server.py#L440)
- 그 아래 파서는 누락된 `top`, `categoryMap`, `body`를 빈 객체·배열로 처리할 수 있다. 따라서 코드 이름과 빈 목록만으로 정상 0건을 보증할 수 없다. [고정 버전 documents.py](https://github.com/hyunae52/korean-taxlaw-mcp/blob/16a08b9af70f49fc60a5f54ab0f9812be206c8f5/src/korean_taxlaw_mcp/domains/documents.py#L189)
- harness의 `normalizeTaxLawResult`는 오류 봉투를 실제 MCP 실패로 올린다. `[OK]`와 `total: 0, items: []`의 정상 응답은 이미 허용한다. [taxLawClient.ts](https://github.com/hyunae52/legal_harness/blob/1e6aa272c8fb24097d67fdf83c7e5d6eade3dd37/src/taxLawClient.ts#L53)
- 연구 경로에는 별도 분류가 있다. `ResearchService`가 일부 검색 예외를 받아 `observeSearch`에 넘기며, 해당 함수는 제한된 국세 검색의 첫 페이지 `NOT_FOUND`를 검색 완료 0건으로 인정한다. 직접 MCP 호출과 연구 호출의 판단 근거를 통일해야 한다. [research.ts](https://github.com/hyunae52/legal_harness/blob/1e6aa272c8fb24097d67fdf83c7e5d6eade3dd37/src/research.ts#L208), [researchSearch.ts](https://github.com/hyunae52/legal_harness/blob/1e6aa272c8fb24097d67fdf83c7e5d6eade3dd37/src/researchSearch.ts#L43)
- 현재 `korean-law-mcp` 4.15.23도 일부 판례 검색에서 결과 0개를 `isError: true`로 반환한다. 도메인별 파서와 검색 보정 경로가 달라 `search_decisions` 전체를 같은 규칙으로 바꿀 수 없다.
- 기존 운영 메일에는 도구와 오류 코드 합계가 있다. 검색어·인수·원시 응답이 없어 과거 `NOT_FOUND`를 새 분류로 소급 확정할 수 없다. 전환 후 집계 시작일과 계약 버전을 명시한다.

## 2. 판정 순서와 결과 계약

판정은 다음 순서를 고정한다.

1. 실제 수행한 작업을 `목록 검색 / 정확한 문서 조회 / 본문 읽기 / 복합 작업`으로 구분한다.
2. 인증·접속·제한·타임아웃·응답 파싱의 실패 여부를 먼저 확인한다.
3. 성공한 목록 응답은 원본 구조, 총건수, 목록, 페이지와 적용 범위를 함께 검증한다.
4. 검증을 모두 통과한 범위에 대해서만 결과 상태를 정한다. 관측하지 못한 값은 추정하지 않는다.

| 결과 상태 | 확인 조건 | 클라이언트 동작 | 메일 표시 |
| --- | --- | --- | --- |
| `found` | 검색 후보 또는 요청 자료를 확보했고 해당 작업의 필수 검증을 통과 | 기존 정상 응답 유지. 후보와 본문 확보는 따로 표시 | 자료 확보 |
| `empty_confirmed` | 검증된 목록 검색의 첫 페이지이며, 원본의 명시적 총건수 0과 빈 목록이 일치 | `isError: false`, `total: 0`, `items: []`. “이 검색 조건·자료원에서 결과 없음” | 정상 검색 0건 |
| `page_out_of_range` | 총건수와 페이지 의미를 검증했고 요청 페이지가 마지막 페이지 이후임 | 정상적인 목록 종료 안내. 전체 검색 0건으로 바꾸지 않음 | 페이지 범위 초과 |
| `document_unresolved` | 정확한 번호·ID로 요청한 문서를 확보하지 못함 | 기존 실패와 확인 안내 유지. “문서가 존재하지 않는다”로 단정하지 않음 | 지정 문서 미확보 |
| `body_unavailable` | 문서 식별·메타데이터는 확보했으나 요청한 본문은 미확보 | 기존 본문 실패 유지. 메타데이터를 본문 성공으로 취급하지 않음 | 본문 미확보 |
| `partial` | 일부 결과만 확보했거나 페이지·필터·변경된 검색 범위의 완전성을 확인하지 못함 | 기존 자료와 제한을 유지. 정상 0건·전체 확인으로 승격하지 않음 | 부분 결과 |
| `failed` | 연결·제한·파싱·입력·내부 처리 등의 확인된 실패 | 원래 오류 코드·안내 유지 | 원인별 실제 실패 |
| `unclassified` | 공급 버전·응답 구조·작업 경로·판정 근거가 지원 범위 밖 | 기존 응답 상태 유지. 정상으로 변환하지 않음 | 원인 확인 필요 |

이 상태는 자료 조회의 결과다. 검색 실행 완료, 후보 발견, 본문 읽기 완료, 법률상 근거 충족은 서로 다른 판단으로 유지한다. `found`도 법률 답변의 정답 판정이 아니다.

### 작업 종류를 도구 이름으로만 결정하지 않는다

- `search_tax_interpretations(document_number=...)`와 `search_tax_decisions(case_number=...)`는 내부적으로 정확한 번호 조회를 한다. 이 호출의 `NOT_FOUND`는 목록 검색 0건으로 바꾸지 않는다.
- `get_decision_text(domain=nts)`처럼 다른 공급 도구로 연결되는 호출도 실제 경로와 작업 종류를 사용한다.
- `execute_tool`은 허용된 내부 도구·인수·결과의 연결을 입증한 경우에만 분류한다. 식별 불가능한 래퍼는 `unclassified`다.
- 복합 검색에서 한 자료원만 성공하거나 일부가 0건인 경우 전체를 `empty_confirmed`로 만들지 않는다. 복합 작업은 최초 적용 대상에서 제외한다.

## 3. 정상 0건으로 인정하는 필수 조건

아래 조건을 모두 충족해야 `empty_confirmed`를 만든다.

1. 고정된 공급 버전, 실제 검색 경로, 지원하는 원본 스키마가 일치한다.
2. HTTP 성공 여부 외에 원본 서비스의 성공 봉투와 필수 구조를 검증했다. 로그인·점검 HTML, 오류 JSON, 빈 문자열, 임의의 `{}`는 대상이 아니다.
3. 원본의 총건수 0을 직접 검증했다. 필드 누락·변환 실패를 기본값 0으로 채우지 않는다.
4. 정상 스키마의 목록이 빈 배열이다. 목록 누락과 빈 배열을 구별한다.
5. 첫 페이지·페이지 크기·원본 페이지 의미가 일치한다. 페이지 정보가 원본에 없다면 그 경로의 명시적 API 계약과 공개 fixture로 확인된 요청 결합 규칙이 있어야 한다.
6. 요청한 문서 분류·세목·기간·필터를 실제로 적용했음을 확인했다. 미인식 세목, 무시된 옵션, 클라이언트에서 일부 행만 거른 결과는 전체 0건 근거가 아니다.
7. 자동 검색 보정·기간 완화·대체 자료원·중간 실패·부분 결과가 섞이지 않았다. 해당 동작 자체는 유지하되 이번 변환에서 제외한다.
8. 정확한 번호 조회나 본문 읽기가 아닌 목록 검색이다.

원본 서비스가 0건에서 특정 필드를 생략한다면 그 형식을 별도 원본 계약으로 입증해야 한다. 실제 응답 fixture 없이 “아마 빈 결과일 것”이라는 예외를 만들지 않는다. 계약이 불분명한 경로는 기존 동작을 유지한다.

### 반드시 별도로 처리할 반례

| 관측 | 판정 |
| --- | --- |
| HTTP 200, 점검 안내 HTML | 파싱/원본 서비스 오류 |
| 빈 JSON, 필수 목록·총건수 누락 | 응답 구조 오류 |
| 총건수 양수, 범위 안 페이지의 목록 0개 | 불완전하거나 모순된 응답 |
| 총건수 0인데 목록에 행 존재 | 응답 구조 오류 |
| 첫 페이지 총건수 0이지만 미인식 세목 또는 무시된 필터가 있음 | 범위 미확인, 정상 0건 변환 금지 |
| 원본 총건수 양수, 일부 행에 날짜 필터를 적용한 뒤 0개 | 해당 페이지에서 후보 미확보; 전체 0건 아님 |
| 총건수 12, 크기 5, 4페이지가 비어 있음 | 검증된 경로라면 `page_out_of_range`; 1~3페이지를 읽었다는 뜻은 아님 |
| 총건수 자체가 0인데 2페이지부터 조회 | 첫 페이지 근거 없음. 최초 버전에서는 정상 0건으로 변환하지 않음 |
| 여러 검색·자료원 중 일부만 성공 | `partial` 또는 해당 실패; 전체 빈 검색으로 변환 금지 |
| 같은 문서가 여러 페이지에서 중복됨 | 중복을 기록하고 완전성 유보. 페이지 끝·전수 확인을 추정하지 않음 |
| 예전 공급 도구의 `[NOT_FOUND]` 문구만 존재 | `unclassified` 또는 작업별 기존 실패 유지 |

## 4. 공급 도구에서 근거를 만들고 harness에서 한 번만 분류한다

### 공급 도구 계약

국세 도구는 `domains/documents.py`에서 원본 구조를 검증하고 `server.py`의 결과 생성 시점에 판정 근거를 붙인다. `not_found`를 만드는 단계까지 총건수·페이지·적용 범위를 버리지 않고 전달한다.

기존 오류 봉투의 코드는 호환을 위해 우선 유지한다. 공급 도구가 생성하는 추가 구조화 필드에는 계약 버전, 실제 작업 종류, 원본 스키마 식별자, 페이지·크기·총건수·반환 수, 범위 확인 여부와 결과 상태만 넣는다. 질문·검색어·인수 전체를 복제하지 않는다. marker는 외부 요청 인수에서 받지 않는다.

법령 공급 도구는 해당 검색 파서가 동일한 수준의 근거를 만들 수 있는 경우에만 적용한다. `node_modules`를 직접 수정하거나 버전 캐시에 패치하지 않는다. 검토된 공급 소스 변경과 릴리스·pin을 사용한다. 공급 도구를 고칠 수 없으면 그 경로는 변환 대상에서 제외하고 미확인 상태를 유지한다.

### harness 분류 경계

`src/retrievalOutcome.ts`를 예상 단일 분류 모듈로 둔다. 실제 호출 문맥, pin으로 검증한 공급 식별자, 공급 결과·예외의 제한된 구조를 받아 추가 I/O 없이 결과를 정한다.

- `LegalRetrievalClient`/`TaxLawClient`의 통합 경계에서 적용해 직접 MCP·REST·연구 경로가 같은 판단을 사용한다.
- `KoreanLawClient`의 예외 경로도 시험한다. 이미 `isError: true`로 던져진 공급 결과를 놓치거나 일반 예외를 빈 검색으로 삼키면 안 된다.
- 정상 0건 변환은 근거 marker와 호출 문맥을 함께 검증한다. marker만 존재하거나 공급 버전이 달라지면 변환하지 않는다.
- 기존 성공 결과의 본문·순서·문서 식별·출처·페이지 연결을 보존한다. 정상 0건의 새 응답은 빈 목록과 제한된 검색 범위를 명시하고 원래 오류 문구를 성공 본문에 섞지 않는다.
- 분류 자체는 원본 공급 도구나 네트워크를 추가 호출하지 않는다. 동일 요청을 자동 재생하거나 새로운 검색어로 확장하지 않는다.
- 분류 모듈은 동기적인 작은 구조 검사로 제한하고, 보고용으로 원시 응답을 다시 파싱·복제·보관하지 않는다.

### 연구 완료 판단과의 연결

`observeSearch`의 첫 페이지 `NOT_FOUND` 특례를 새 근거 계약과 연결한다. 새 모드에서 근거 없는 `NOT_FOUND`만으로 `total=0`, `status=complete`를 만들지 않는다. 기존 coverage 알고리즘·요건·추가 페이지·반대 근거 확인 규칙은 유지한다.

정상 빈 검색이 기존의 다른 검색 단계를 이어갈 수는 있다. 하지만 빈 검색 하나가 연구 전체 완료, 반례 부재, 법률 결론의 확정으로 전파되면 실패다. `page_out_of_range`도 읽지 않은 앞 페이지의 의무를 충족시키지 않는다. 본문 미확보·부분 자료는 근거 채택 완료가 될 수 없다.

원래 오류로 중단되던 연구가 정상 0건을 받고 기존 후속 단계를 수행하면 전체 호출 수는 달라질 수 있다. 이 변화는 별도로 검증한다. 개별 조회에는 추가 호출이 없어야 하며, 연구 전체는 기존 정상 0건 fixture 대조군과 같은 후속 단계·예산을 지켜야 한다. 새 분류 때문에 별도의 재검색 절차를 추가하지 않는다.

## 5. 최초 적용 범위와 변경 단위

### 적용 순서

1. 국세 `search_tax_interpretations`, `search_tax_decisions`의 일반 목록 검색부터 검증한다. 정확한 번호 조회 옵션과 `curated_issue`, `audit_appeal`, `taxpayer_protection` 등 별도 모듈 경로는 제외한다.
2. 법령 `search_decisions(domain=precedent)`의 원본 검증과 보정 이력을 명시할 수 있는 경로를 별도 검토한다. 보정·본문 결합 경로를 자동으로 포함하지 않는다.
3. 지방세, 다른 판례 도메인, 법령 검색, `execute_tool`, 복합 도구는 각각의 계약 fixture와 검증을 갖춘 뒤 별도 확장한다.

각 경로는 독립적으로 활성화한다. 특정 도구 이름 전체나 모든 `NOT_FOUND`에 일괄 적용하지 않는다. 과거 메일의 정상 0건 전환 가능 건수는 현재 자료로 산출하지 않는다.

### PR 단위

| 단계 | 범위 | 통과 조건 |
| --- | --- | --- |
| A | 공급 원본 검증, typed outcome 근거, 정상·비정상 fixture | 잘못된 응답이 정상 0건이 되지 않고 기존 자료 조회가 유지됨 |
| B | 공통 분류기, 호출 문맥 결합, MCP·REST·연구 연결 | 같은 사례의 분류 일치, 빈 검색만 의도대로 정상화, 법률 검수 기준 유지 |

판례 본문 대기 대상 확대는 별도 개선 후보다. 이 분류 변경에 동시 처리 수·큐 크기·대기시간·재시도 정책 변경을 섞지 않는다. 자료를 실제로 더 찾게 하는 검색 품질 개선 역시 공개 재현 사례를 확보한 별도 수정으로 다룬다.

## 6. 메일과 집계 정의

기존 호출 수와 원본 오류 코드 기록은 유지한다. 기존 성공·실패 합계는 실제 반환된 MCP 상태를 센다. 정상 0건 반환 방식이 바뀌면 성공률의 정의상 수치가 달라질 수 있으므로 전환일·버전을 표시하고 검색 적중률 향상으로 표현하지 않는다.

메일에는 다음 두 표를 구분한다.

1. **실행 결과:** 호출 수, 프로토콜·응용 오류, 제한·연결·파싱 등 원인. 기존 집계와 정의를 명시한다.
2. **자료 조회 결과:** 자료 확보, 정상 검색 0건, 페이지 범위 초과, 지정 문서 미확보, 본문 미확보, 부분 결과, 원인 확인 필요.

조회 대상 호출 하나당 결과 상태 하나만 기록한다. 하위 공급 호출은 기존 `source` 범주에서 별도로 세며 MCP 합계와 합산하지 않는다. 검수·PR 도구 등 비조회 호출은 조회 결과 표의 분모에서 제외한다. 재호출은 새 호출이고, 수집 누락은 정상이나 0건으로 채우지 않는다.

분류 집계는 앞선 개발 측정 계획의 독립 저장 경로 중 필요한 최소 부분을 사용한다. 기존 usage DB의 스키마·트랜잭션을 이 기능 때문에 변경하지 않는다. 수집기가 없거나 장애면 기능은 계속 동작하고 상세 표는 미수집/부분 집계로 표시한다. 전체 모델 평가 기능이 완료될 때까지 정상 0건 개선을 묶어 대기시키지는 않는다.

저장은 등록 도구, 작업 종류 enum, 결과 enum, 고정 원인 코드, 공급·분류 계약 버전, 일자와 개수에 한정한다. 검색어·문서 내용·원시 오류·식별자·인수 해시는 저장하지 않는다. 추가 집계·메일 실패는 응답·provider 호출 수·drain에 영향을 주지 않는다. 새 상세 집계와 기존 메일을 연결할 때는 기존 06:00 예약·중복 발송 방지·수신자를 유지한다.

필수 합격 조건은 O01~O16 통과, 지원 경로의 공용 fixture에서 **거짓 정상 0건 0건**, 기존 정상 조회 손실 0건, 분류 자체의 추가 원본 호출 0회다. 연구 후속 호출은 위 정상 0건 대조군의 기존 규칙·예산과 일치해야 한다. 이는 시험한 사례에 대한 합격 기준이며 모든 실제 입력의 무오류 보장을 뜻하지 않는다.

기존 `npm run review`, `review:package`, runtime audit, secrets 검사와 정확한 후보의 Node 22 CI를 통과한다. `tests/taxlaw-client.test.mjs`, `authority-coverage.test.mjs`, `provider-diagnostics.test.mjs`, usage/메일/취소·종료 관련 기존 계약을 포함한다. 법률 검수 기준을 약화시키는 방식으로 기존 테스트를 바꾸지 않는다. legacy NOT_FOUND 특례 테스트는 새 근거 유무를 각각 검증하도록 명시적으로 교체한다.

## 8. 활성화와 되돌리기

제안 설정은 `TAXLAB_SEARCH_OUTCOME_V1`이며 기본값은 비활성이다. 이 이름은 구현 전 검수에서 확정한다. 공급 경로별 허용 목록과 정확한 pin/계약 버전이 모두 맞아야 적용한다.

1. Pro가 계획·반례·범위를 검토하고 실제 `PLAN PASS`를 반환한 뒤 구현한다.
2. 비활성 상태에서 기존 동작을 확인한다. 별도 원본 호출 없이 이미 처리된 결과에 대해서만 예상 분류를 관측할 수 있다.
3. 공개·합성 사례의 로컬·스테이징 검증과 정확한 배포 후보 검증을 끝낸다. 검증 때문에 운영 트래픽을 재생하지 않는다.
4. 준비된 경로 하나씩 활성화하고 응답·연구 상태·원인 분포·기록 누락을 확인한다.
5. 정상 조회 손실, 거짓 정상 0건, 근거 없는 연구 완료, 분류 자체의 추가 원본 호출 또는 기존 연구 예산 초과가 확인되면 해당 경로를 비활성화한다. 비활성화는 상세 집계 DB migration에 의존하지 않는다.
6. 공급 파서의 stricter 검증 자체가 정상 자료를 거절하면 harness flag만으로 복구되지 않을 수 있다. 이전 공급 pin과 harness 패키지를 함께 보존하고 그 조합의 되돌리기를 별도 시험한다.

공급 업데이트로 pin이나 스키마가 바뀌면 새 검증 없이 정상 0건 변환을 이어가지 않는다. 자동 업데이트 자체는 유지하고, 미검증 조합은 기존 응답으로 동작하며 운영 보고에 미지원 계약임을 표시한다.

## 9. Pro 검수 요청

이 계획과 지정한 소스를 읽기 전용으로 검토한다. 구현·명령 실행·PR 작성·배포·메일 전송을 요청하지 않는다.

반드시 검토할 질문:

1. 누락 필드·오류 봉투·다른 경로를 정상 0건으로 오인하는 반례가 남았는가?
2. 정확한 번호 조회, 마지막 페이지 이후, 본문 없음, 검색 보정·필터 무시가 각각 구별되는가?
3. 기존 NTS `NOT_FOUND` 특례를 바꾸면서 직접 MCP와 연구 검수의 의미가 어긋나지 않는가?
4. 공급 pin·계약 변경, 기능 flag, 단계별 배포·되돌리기가 실제 오류를 숨기지 않는가?
5. 집계 누락·혼합 버전·모드 변경을 성공률 개선으로 잘못 표현하지 않는가?
6. 추가 원본 호출·자동 재검색·기존 처리 한도 변경 없이 목표를 달성하는 최소 변경인가?

`PLAN PASS` 또는 `PLAN REVISE`와 구체적 반례·수정안을 요청한다. 실제 응답을 받기 전까지 검수 완료로 표시하지 않는다.
