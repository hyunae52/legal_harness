# 개발용 단계별 측정과 상세 이메일 계획

상태: PLAN PREPARED. Pro에 아직 제출하지 않았으며 검수 통과 전 측정 기능은 구현하지 않는다.
작성일: 2026-11-04 KST.

## 1. 목표와 가장 중요한 제약

검색 → 원문 확보 → 근거 채택·적용 → 제출 초안의 어느 단계에 개선 여지가 있는지 개발자가 확인한다.
기존 검색 결과, 법률 검수 상태, 성공·실패 판정, 응답 형식, 처리 한도, 사용자 동선을 유지한다.
측정과 메일의 실패는 기존 요청에 대한 실패·재시도·유보·추가 질문으로 전달되지 않아야 한다.

이번 구현에 검색어 확장, 검색 순서 강제, 새 법률 판단 규칙, 새로운 사용자 통과 조건,
자동 교정 PR 생성·병합, 모델별 검색 경로의 통일은 포함하지 않는다.
기존 조건·예외 검사를 다시 만들지 않는다. 개선 PR은 관측된 문제를 검토한 이후 별도로 결정한다.

## 3. 측정은 두 경로로 구분한다

### A. 개발자가 실행하는 평가

공개 자료 또는 합성 사실관계로 만든 고정 사례를 격리된 로컬/CI 서버에서 실행한다.
사례별 기대 문서·인용·조건·시점·답변 요구사항을 사람이 검토하여 버전 관리한다.
모델이 실제로 어떤 검색어와 순서를 선택했는지는 진단 자료이며 그 자체를 통과 조건으로 고정하지 않는다.
같은 자료·버전·예산을 사용한 결과와 근거 충족 여부를 비교한다.

원문 조회를 재실행하는 live 평가와 저장된 fixture 평가는 분리하고 수행 날짜를 표시한다.
실서비스 트래픽을 재생하거나 외부 모델 API를 자동 호출하지 않는다. 새 API 키도 요구하지 않는다.
모델 실행을 포함한 결과는 개발자가 명시적으로 만든 평가 산출물을 읽는다.
실행하지 않은 모델 또는 사례의 점수는 생성하지 않는다.

### B. 운영에서 발생한 구조화된 관측 로그

기존 처리에서 이미 확인된 고정 코드·수치만 추가로 기록한다. 운영 검색을 추가 실행하지 않는다.
각 단계의 독립적인 건수와 오류 분포를 보여주며, 관측하지 못한 단계는 `not_observed`로 남긴다.
세션 연결키를 영속 보관하지 않으므로 운영 로그만으로 사용자별 전체 조사 성공률을 만들지 않는다.
단계별 빈도와 개발 평가의 사례별 점수는 메일에서 서로 다른 표로 표시한다.

| 단계 | 운영에서 관측할 값 | 개발 평가에서 확인할 값 | 해석 제한 |
| --- | --- | --- | --- |
| 검색 | 완료·오류·0건·부분 검색, 후보 수, 기존 검색 범위 코드 | 기대 문서 발견 여부와 자료 집합에 대한 recall | 0건은 법적 근거·반례의 부재가 아님 |
| 원문 | 본문 반환·부분·접근 불가·해석 실패, 완전성 표시 | 기대 문서와 본문·조문·문서번호의 일치 | 반환 성공과 전체 원문 확보를 구분 |
| 근거 채택 | 검수에 제출된 채택·배경·유추의 개수, 미해결 후보 수 | 결론에 필요한 근거의 채택, 반대 근거 처리 | 클라이언트의 선언은 독립적 법률 판단이 아님 |
| 적용·조건 | 기존 요건·시점·예외의 미해결 수, 기존 검수 코드 | 사례에 필요한 조건·예외·시점의 연결 | 기존 판단 결과를 변경하거나 재판정하지 않음 |
| 제출 초안 | 기존 구조 검수 상태, 검수 접수 여부 | 기대 답변 요구사항, 근거 없는 단정·누락 | 제출 초안과 사용자에게 전달된 최종 답변을 구분 |
| 최종 답변 | 기본 `not_observed` | 명시적으로 제공된 평가 답변만 검토 | 실제 클라이언트 답변을 수집했다고 주장하지 않음 |

분모는 항상 함께 출력한다. 예: 본문 확보율의 분모는 본문 요청이며 검색 호출을 섞지 않는다.
전송 성공률, 자료 확보율, 구조 검사 결과, 사례 평가 점수는 하나의 성공률로 합산하지 않는다.
부분 자료, 수집 누락, 오래된 평가, 판정 불가를 성공이나 0건으로 대체하지 않는다.

## 4. 기존 기능과 분리하는 구현 경계

1. 기본 비활성 설정 `TAXLAB_DEV_MEASUREMENT_DB`를 추가한다. 설정이 없으면 worker·파일·네트워크를 만들지 않는다.
2. 기존 작업이 결과 또는 오류 코드를 확정한 뒤 고정 크기의 관측값만 전달한다.
   측정 때문에 응답 본문을 복제·직렬화하거나 추가 원문을 읽지 않는다.
   원문·질문 객체를 측정 모듈에 넘기지 않도록 입력 타입부터 제한한다.
3. 기록은 별도 worker와 별도 DB를 사용한다. 기존 usage DB의 스키마·쓰기 transaction을 변경하지 않는다.
   요청 경로에서 DB, SMTP, 파일 쓰기, 네트워크, worker 준비를 기다리지 않는다.
4. 전송은 예외를 내부에서 처리하는 비동기 큐로 제한한다. 준비 전·큐 포화·worker 종료 때 관측값만 버린다.
   큐는 최대 128건, 건당 1 KiB 이하의 고정 스키마, 미확인 전송을 포함한 전체 메모리 상한을 둔다.
   worker에 무제한 `postMessage`를 보내지 않도록 승인 크기와 미확인 건수를 추적한다.
5. worker 장애를 사용자 요청으로 전달하거나 서비스 종료 원인으로 사용하지 않는다.
   같은 프로세스에서 무한 재시작하지 않고 기록을 중단하고 누락 상태를 운영 보고에 남긴다.
6. close·타임아웃·취소·drain·요청 처리 슬롯 해제는 기존 경로를 유지한다.
   종료 시 측정 flush를 기다리느라 기존 drain을 지연하지 않는다. 미저장 관측값은 손실 가능성을 표시한다.
7. 공개 도구·인수·스키마·응답·지침·health 계약을 측정 때문에 변경하지 않는다.
   읽기 전용 운영 CLI와 별도 상세 메일로 상태를 확인한다.

관측 경계 후보는 `ResearchService`의 완료된 검색/원문 commit 경계와 검수 반환 경계다.
`app.ts`의 공통 호출 경계에서는 호출 메타데이터만 취한다. 같은 작업을 여러 경계에서 중복 집계하지 않는다.
검색 시도와 캐시 재사용, 사용자 재호출, 검수 재제출을 서로 다른 정의로 명시한다.
새로 집계하기 위해 `inspectResearch`, `coverage`, 원문 파서를 다시 실행하지 않는다.
관측 때문에 결과 확정 전에 발생할 수 있는 예외 경로가 생기는지 Pro가 특히 검토한다.

## 5. 저장 범위와 크기 제한

저장 허용: 완료 시간, 단계 enum, 서버 등록 도구, 허용된 상태·오류 코드,
기존 결과에서 얻은 개수·완전성 flag·지연 구간, 배포 커밋·provider/정책/schema 버전.

저장 금지: 질문·검색어·인수·답변·초안·원문·원시 오류·문서 URL·개인 사실관계,
actor/IP/session/client_session/research_id, 인증값, 환경 변수, 위 값들의 단순 해시.
문서별 사례 분석은 공개·합성 개발 fixture에서만 한다. 비공개 운영 원문을 메일에 붙이지 않는다.

클라이언트 모델은 증명할 수 없으면 `unknown`이다. 모델 문자열을 새 필수 인수로 요구하지 않는다.
개발 평가에서 확인된 모델·설정·예산과 운영의 미확인 클라이언트를 섞지 않는다.

파일은 배포 경로 밖 전용 디렉터리 0700, DB/상태 파일 0600으로 둔다.
제안 상한: 관측 기록 14일·32 MiB, 집계 90일·64 MiB, 상세 보고 산출물 30일·32 MiB.
실제 row 상한, DB/WAL/checkpoint 상한과 prune 비용은 구현 전 Pro 검토에서 확정한다.
보관 정리·집계는 worker/별도 작업에서만 수행한다. 디스크 부족 시 서비스 대신 기록을 중단한다.
누락 건수·수집 시작·마지막 저장·worker 상태는 보고의 필수 필드다. 재시작 전 손실을 복원했다고 하지 않는다.

## 6. 상세 이메일 구성

기존 사용량 메일과 업데이트 알림은 유지하고 개발용 상세 리포트를 별도 생성한다.
기존 private 수신자 파일과 SMTP 설정을 재사용하며 공개 저장소에 주소·비밀번호를 추가하지 않는다.
발송 예약은 매일 06:00 KST, 대상은 직전 닫힌 06:00~06:00 구간이다.
저장 지연을 확인할 수 있도록 마지막 저장 시각과 누락 여부를 포함하고 미완전 구간은 부분 집계로 표시한다.

메일 내용:

1. 기간·수집 범위·배포/도구 버전·집계 누락·평가 실행 시각을 먼저 표시한다.
2. 단계별 분모/건수/비율과 `not_observed`, 오류/0건/부분 자료를 분리한 표.
3. 단계·도구·고정 오류 코드별 상위 문제, 전일/7일 변화와 해당 표본 수.
4. 새 버전 전후를 버전별로 나눈 집계. 버전·모델·예산이 달라진 비교는 제한을 표시한다.
5. 개발 평가의 사례별 기대 결과·실제 관측·실패 단계·근거 artifact 경로와 재현 명령.
6. 개발자가 검토할 후보와 아직 판정할 수 없는 사항. 자동 해결·자동 PR 통과로 표현하지 않는다.
7. 수집기·저장·발송 상태와 보고의 실제 데이터 범위.

HTML 요약과 전체 허용 항목을 담은 JSON/CSV 첨부를 만든다. 크기 상한과 생략 건수를 표시한다.
보고 생성 실패를 호출 0건/정상으로 바꾸지 않는다. 운영자가 원인을 알 수 있는 고정 오류 코드로 보고한다.
일자·수신자·보고 종류별 독립 발송 장부를 사용한다. 동시 실행은 한 번만 발송한다.
SMTP 결과가 불확실하면 pending을 보존하며 자동 중복 발송하지 않는다. 원시 SMTP 오류를 저장하지 않는다.
메일 생성·SMTP는 앱 요청 프로세스 밖에서 실행하고 CPU/메모리/실행시간을 제한한다.

## 7. 파일과 변경 단위

예상 신규 파일: `src/devMeasurement.ts`, `src/devMeasurementWorker.ts`,
`src/devMeasurementReport.ts`, `src/devMeasurementMail.ts`,
`eval/README.md`, `eval/cases/*.json`, `scripts/run-dev-evaluation.mjs`, 전용 deploy service/timer, 관련 테스트.

예상 최소 수정: `src/index.ts`의 선택적 초기화, `src/app.ts`와 `src/research.ts`의 관측 전달 경계,
필요한 경우 기존 함수가 이미 계산한 비민감 primitive를 내부 observer에 전달하는 선택적 옵션.
기존 검수 알고리즘과 공개 schemas, provider 코드, usage 저장/메일 구현은 수정하지 않는다.
관측값을 얻기 위해 기존 의미·처리 순서를 바꿔야 한다면 해당 지표를 이번 버전에서 제외한다.

PR은 (1) 평가·보고 형식과 격리 저장, (2) 최소 관측 연결·회귀 검증,
(3) 운영의 선택적 활성화와 메일 설정으로 나눈다. 각 단계의 산출물·검증을 따로 남긴다.
실제 파일 분할은 Pro 피드백을 반영하되 위 기능 경계는 유지한다.

| 활성/장애 | 기록 모듈 예외, DB 잠금·디스크 부족, worker 종료·정지, 큐 포화에서 같은 결과/오류/취소/호출 수 |
| 격리 | 정상·장애 수집기 모두 요청 slot, drain, 외부 조회 횟수, 기존 usage 합계를 변경하지 않음 |
| 성능 | 같은 fixture/동시성의 활성·비활성 대조, 관측 전송 p99 1 ms 이하를 초기 목표로 측정; 초과 시 활성화 보류 |
| 자원 | 입력 문자열 공격, 무한 미확인 전송, 버전 cardinality, 보관일 경계에서 상한이 유지됨 |
| 데이터 | 질문/주소/세션키/토큰 canary가 DB/WAL/보고/오류 로그 어디에도 기록되지 않음 |
| 지표 | 0건·오류·부분·취소·재호출·재검수·unknown 모델·미관측 답변을 구별하고 분모/중복 규칙이 맞음 |
| 이메일 | 06시 경계·부분 수집·저장 지연·중단 후 재개·동시 발송·불확실 SMTP·크기 제한·HTML escaping |

Pro PLAN PASS와 지적 사항의 근거 확인 후 구현한다. 코드 변경 후에는 해당 후보의 로컬/CI 결과와
실제 diff를 근거로 검토한다. 최초 배포는 측정 비활성 상태로 기존 기능을 확인한다.
이후 같은 릴리스에서 관측만 활성화하고 자료 조회·MCP 응답·자원 사용·보고 미리보기를 확인한다.
설정 확인용 메일은 실제 수신자를 확인한 뒤 1회 보내고 수락 영수증을 검증한다.
기능/성능에 영향이 보이면 측정을 비활성화하고 기존 서비스만 유지한다. 롤백은 측정 데이터 migration에 의존하지 않는다.

## 9. Pro에게 요청할 검수

이 계획과 지정한 기준 소스만 읽기 전용으로 검토한다. 파일 변경, 명령 실행, PR/메일/배포는 요청하지 않는다.
기존 기능의 무간섭, 실제 관측 가능성, 실패 격리, 데이터 최소화, 메모리/디스크 상한,
지표의 분모와 중복, 모델 차이, 메일의 누락/중복, 단계별 활성화가 충분한지 판단한다.
부족한 사항은 구체적 반례와 최소 수정안으로 제시하고 `PLAN PASS` 또는 `PLAN REVISE`를 반환한다.
자료를 읽지 못하면 접근하지 못한 파일과 판단 한계를 명시한다.

참고: [Upstage 평가 구성](https://github.com/UpstageAI/korean-tax-mcp/tree/982132d92895e4b66401a11ec997651e93fc6fbf/eval).
단계별로 실패를 분리하는 접근을 참고하며 외부 프로젝트의 점수나 법률 정답을 우리 성능으로 가져오지 않는다.
