서버가 **사실값의 출처**와 **그 사실이 왜 법적 판단에 필요한지**를 구별하지 않는 것이 보완 지점이다. 기존 안내에 실제 미확인점만 적으라는 문구는 이미 있으므로 문구 추가만으로 해결됐다고 보지 않는다.

## 2. 지킬 범위와 판정 기준

- 외부 LLM이 추론하고 MCP는 조회·증거·검수 절차를 제공한다. 새 서버 LLM 키·DB·사용자 수 제한은 도입하지 않는다.
- 40회 원천 조회, 32개 저장 단위, 기존 바이트 예산·TTL, 시험당 1,500초와 원래 시나리오 입력을 유지한다. 후보를 상위 N개로 잘라 완료시키거나 오류를 0건으로 바꾸지 않는다.
- **답변을 끝냈는지, 조사를 완료했는지, 법적 결론이 근거에 맞는지는 별도**다. 공백을 알리는 답변은 필요하지만 정상 대조의 완료를 대신할 수 없다.
- 구법 판결과 신법 사건의 구별, 판례·예규 권위 구별, 제공되지 않은 사실·일자의 보존, 단순 조회의 인터뷰 면제를 유지한다.
- 기존 `pilot-i` 2개 실패는 보존한다. 같은 코드에서 실패 입력만 반복 실행해 성공 기록으로 교체하지 않는다.

## 3. 수정 A — 같은 revision의 원문 귀속을 추가 방식으로 복구

**가장 먼저 적용할 작은 수정이다.** 대상: `research.ts`의 원문 binding·재사용, `researchCoverage.ts`의 공유 맥락 회귀 검증.

1. 같은 revision에서 재사용은 현재 유효한 귀속과 요청한 쟁점의 **합집합**으로 처리한다. `[I1,I2]`에 `[I3]`를 추가하면 `[I1,I2,I3]`가 된다. 법령 원문과 원래 쟁점 연결을 빼지 않는다.
2. 과거 revision의 원문을 처음 재연결할 때에는 새 revision에서 명시한 쟁점만 사용한다. 이전 revision의 적용 범위를 자동으로 되살리지 않는다. 그 뒤 같은 revision에 대한 추가 재사용만 합집합이다.
3. 같은 연결의 재전송은 원천 재조회·바이트 복제·추가 검색 성공을 만들지 않는다. 실제 귀속 변경은 state와 검수 해시를 갱신한다. 완전히 같은 연결이면 불필요한 상태 변경도 하지 않는다.
4. 원문 해시·최초 조회 시각·manifest·source revision은 그대로 둔다. 다른 사건·다른 actor·불완전한 manifest는 재사용할 수 없다.
5. 검색 맥락 공유는 현재 관측된 동일 법령·조문 연결 안에서만 작동한다. 별도 법령이나 다른 문서로 취득 순서 검색어가 전파되지 않도록 검사한다.

원문 귀속을 제거해야 하는 실제 범위 변경은 기존 계획 수정·revision 변경 경로로 처리한다. 재사용 호출을 암묵적 삭제 기능으로 사용하지 않는다.

## 4. 수정 B — 같은 연구에서 수정·종료할 수 있는 응답

대상: `research.ts`, `researchProgress.ts`, `researchContracts.ts`, 공통 오류 응답 및 MCP·REST·Actions 표현.

### B-1. 용량 오류에 원인과 가능한 다음 행동을 표시

기존 오류 코드와 HTTP 의미는 유지하고, 소유권 확인 뒤 제한된 `capacity_reason`과 `recovery`를 추가한다. 조회 횟수, 작업 수, 원문 단위, 본문 바이트, 메타데이터 바이트, 세션/공유 예약 부족을 구분한다. 다른 사용자의 연구 내용·식별값은 반환하지 않는다.

`recovery`는 현재 revision/state, 실행 중 여부, 남은 예산, 저장 원문 읽기·입력 수정·검수 가능 여부, 다음 행동을 보여준다. 소진된 한도에 같은 요청을 다시 보내도 새 원천 호출을 하지 않는다. 실제 실행 중인 작업은 그 작업의 결과를 기다리고, 동일 request ID는 기존 결과로 돌아간다.

저장 한도로 수락할 수 없는 작업은 원천 호출 전에 거절한다. 이미 수락한 작업의 실패 종료 기록·예약 정리 공간은 확보한다. 예산 소진 뒤에도 저장 원문 읽기와 조건부 초안 검수는 가능해야 한다. 문서가 실제로 없는 경우나 기록 한도가 꽉 찬 경우는 완료로 바꾸지 않는다.

새 연구를 자동으로 만들어 우회하는 기능은 넣지 않는다. 서로 다른 사용자 질문을 문구만 보고 합치지도 않는다. 기존 세션을 이어갈 수 있는 때에는 재개 경로를 안내하고, 만료·프로세스 재시작으로 정말 유실됐을 때만 복구 불가능 사유를 표시한다.

### B-2. 진행 응답과 원문 읽기를 분리

일반 진행·수정 응답은 상태와 다음 행동을 우선 반환한다. 초기 목표 계약은 **UTF-8 JSON 진행 요약 32KiB 이하**, 앞부분의 `client_session`·research ID·revision/state 보존이다. 본문·전체 계획·전체 이력을 이 요약에 반복 삽입하지 않는다. 이 수치는 새 응답 형식의 설계·시험 기준이며 달성 실측값이 아니다.

필수 작업·오류·참조 목록이 한 응답에 안 들어가면 개수와 snapshot에 묶인 다음 페이지를 명시한다. 숨긴 항목이 없다고 표시하거나 최신 N개만으로 검수하지 않는다. 실제 검수는 전체 서버 상태로 한다.

`get_legal_research`의 명시적인 원문 선택 조회는 정확한 저장 본문과 hash/manifest를 돌려준다. 계획·이력 조회도 명시적으로 선택할 수 있게 한다. 큰 명시 조회는 기존 응답 상한과 완전성 표시를 지킨다. 요약·선택·페이지 응답이라는 표식을 두어 일부 목록을 전체 원장으로 오인하지 않게 한다. 기존 전체 객체를 기대하는 클라이언트 영향은 정책 버전·도구 설명·채널 통합 검사에 포함한다.

현재 원장 내부의 검색 hit와 후보 중복 저장까지 이번에 전면 재설계하지 않는다. A 수정으로 폭증 원인을 제거하고 B 응답을 줄인 뒤에도 정상 사례가 저장 예산에 걸리는지 측정한다. 계속 걸리면 보존 의무를 지키는 별도 저장 구조 수정의 근거로 삼는다.

### B-3. 검수 오류를 바로 수정할 수 있게 반환

`FACT_NOT_FOUND`에는 현재 등록된 사실 ID, 날짜 참조 오류에는 별도의 날짜 역할 목록을 연결한다. 근거·후속 검색·버전 오류에도 현재 세션에서 사용할 수 있는 참조 위치를 안내한다. 서버가 인용문을 이어 붙이거나, 날짜를 사실로 임의 변환하거나, 법적 적용 결론을 대신 채우지는 않는다.

다음 행동은 자료 조회, 저장 원문 읽기, 입력 수정, 요건 검토, 실행 중 작업 대기, 검수 또는 공백을 명시한 답변 작성으로 구분한다. `answer_with_gaps`는 법률 결론·조사 완료 판정이 아니다. 현재 정책상 더 조회할 수 없는 상태에서 조회를 반복 권고하지 않는다.

## 5. 수정 C — 미확인 사실을 필수로 요구하는 근거를 검토

대상: `researchContracts.ts`, `researchInterview.ts`, `researchReview.ts`, `scopeCompletion.ts`와 작은 공통 요건 판정 모듈. 새 MCP 도구를 추가하기보다 기존 계획 갱신 도구를 확장한다.

### C-1. 사실과 필요성 평가를 분리

`facts`의 provided/unknown/assumed와 값은 유지한다. **unknown을 답변 편의를 위해 provided로 바꾸지 않는다.** 미확인 필수 사실·날짜에는 서버가 revision·쟁점·대상 ID에 연결한 `requirement_id`를 부여하고 다음 세 상태로 평가한다.

| 상태 | 의미와 처리 |
| --- | --- |
| `unresolved` | 필요하다고 가정했지만 근거를 아직 확인하지 않았다. 먼저 원문·요건을 조사하고, 이를 확정된 법적 조건처럼 사용자에게 질문하지 않는다. 검토가 필요한 가설을 삭제해 완료시키지도 않는다. |
| `required` | 현재 질문을 판단하는 데 필요한 사실이다. 근거는 현재 원문 인용·적용 버전·쟁점 연결 또는 서버가 관리하는 해당 프로필의 요구 항목이다. 실제 값이 없으면 질문하거나 공백을 유지한다. |
| `not_required_for_question` | 이 질문의 결론을 막는 조건으로 사용하지 않는다. 원문과 요청 범위에 대한 제외 이유를 남긴다. 사실 자체는 unknown으로 보존하며 그 요건이 모든 사건에서 없다고 선언하지 않는다. |

모델의 `required_fact_ids` 선언만으로는 `required`를 확정하지 않는다. 기존 입력은 받아서 필요성 미분류 항목으로 연결한다. 사용자 진술의 출처나 query의 인용은 질문 범위·사실의 근거일 뿐 새로운 법적 요건을 만드는 근거가 아니다. 프로필 근거도 모델이 임의 문자열로 발급할 수 없다.

자료·버전·사실·범위가 부족해서 필요한지 모르는 상황은 `unresolved`다. 단순히 검색에서 못 찾았다는 이유로 `not_required_for_question`으로 바꿀 수 없다. 반대로 현재 원문에 없는 막연한 ‘다른 요건’을 확정된 사적 사실 질문으로 유지할 수도 없다.

### C-2. 근거를 등록·교정해도 원천 조회를 처음부터 반복하지 않기

`update_legal_research`에 **요건 평가만 갱신하는 명시적 입력 분기**를 추가한다. 전체 계획 변경과 구별하고 `expected_revision`과 `expected_state_version`을 모두 검사한다. 입력에는 대상 requirement ID, 판정, 근거 종류, 현재 원문 인용, 이유를 포함한다.

사실·날짜·쟁점·질의 범위를 그대로 두고 필요성 평가만 갱신하는 경우 revision은 유지하고 state version과 검수 해시는 바꾼다. 실제 검색·원문·조회 시각은 유지하며 검수만 다시 한다. 새로운 검색 의무가 생기면 실제 이행 전까지 미완료다. 사실·범위·앵커가 바뀌는 전체 계획 변경에는 기존 revision 무효화 규칙을 적용하고 영향받은 평가도 재확인한다.

요건 평가는 기존 세션/메타데이터 예산에 포함하며 레코드 수·문자열 크기를 제한한다. 원문을 평가 레코드에 복제하지 않고 evidence/passage 참조를 사용한다. 필요한 상태를 저장할 수 없으면 B의 정확한 용량 사유를 반환한다.

### C-3. 질문·검수·최종 유보가 같은 근거를 사용

인터뷰, 검수, 범위 완료 판정이 같은 유효한 요건 평가를 사용한다. 등록 직후의 가설은 원문 조사 대상으로 안내하고, `required`인 사적 사실만 사용자 질문으로 전환한다. 프로필의 진짜 필수 사항이나 실제 조문의 확인되지 않은 조건은 계속 남긴다.

이미 등록된 요건은 ID를 바꾸거나 필수 목록에서 빼는 것만으로 해소되지 않는다. 계획 수정 시 이전 항목과의 대응·철회 이유를 보존하고, 새 범위에서의 필요성 판단으로 연결한다. 실제 사용자 요청 범위가 달라진 경우의 정당한 제외와, 알려진 공백을 지우는 행위를 구분한다. 이력도 기존 저장 예산 안에 둔다.

자유서술 `unknowns`·예외 설명·유보 사유에 조건을 옮겨 같은 문제를 우회하지 않도록, 결론을 막는 항목은 등록된 요건 또는 서버가 관측한 자료 공백의 ID와 연결한다. 일반적인 법률 검증 한계와 요청 밖 주의사항은 별도 범위 설명이다. 기존 형식은 공백을 안내하며 수용하되, 대응되지 않은 유보 조건을 법적 요건으로 인증하지 않는다.

이 연결은 선언된 근거의 존재·유효성을 검사하는 것이다. 근거 ID 하나를 붙였다는 이유로 자유서술 전체가 의미상 정당하다고 판단하지 않으며, 최종 자연어 답변이 제출한 구조와 다른 조건을 말하는지도 실제 모델 출력의 의미 검수에서 확인한다.

서버가 확인할 수 있는 것은 실제 원문, 정확한 인용, 버전·쟁점·소유권, 평가 이력과 참조의 일관성이다. **인용이 요건을 의미상 뒷받침하는지까지 결정적으로 증명하지는 못한다.** 모델이 무관한 문장을 근거로 잘못 판단할 가능성은 독립 의미 검수와 실제 모델 평가로 확인한다. 따라서 필드를 채우는 것만으로 I-2 통과라고 선언하지 않는다.

## 7. 구현·검수·재평가 순서

1. **계획 검수:** 이 문서, 새 근거 JSON, 기존 평가·테스트 증거를 Pro에 전달한다. 핵심 질문은 A의 revision 경계, B의 종료/부분 응답 계약, C의 근거 없는 유보와 실제 미확인 사실의 구별이다. 과거 계획 승인을 이번 계약 승인으로 사용하지 않는다.
2. **A 먼저 수정:** CF-01~03의 RED→GREEN을 확보한다. 원문 재사용 버그를 먼저 고쳐 광범위 검색이 생기는 경로를 제거한다. 아직 24회 모델 평가를 시작하지 않는다.
3. **B·C 수정:** 각 영향 경계의 표적 검사와 반대 사례를 고정한 뒤 구현한다. 참고 파일은 기존 `tests/research-harness.test.mjs`, `tests/public-access.test.mjs`, `tests/research-rollout.test.mjs`, `tests/scope-completion.test.mjs`다. 필요하면 요건 검사만 작은 별도 테스트 파일로 분리한다.
4. **배치 전 점검:** 모든 수정이 같은 스냅샷에 모이면 관련 전체 검사, 패키지 설치 검사, 실패 원문을 이용한 제한된 흐름 재생을 수행한다. 재생은 모델 시험 통과로 세지 않는다. 제품·계약 변경이 없으면 같은 검사를 검수 단계마다 반복하지 않는다.
5. **한 번의 고정 평가 배치:** 소스·컴파일된 런타임·모델·프로토콜을 고정하고 원래 8사례×3회를 모두 실행한다. 시나리오 프롬프트·정답 힌트·1,500초 제한은 유지한다. 새 서버의 도구 스키마·오류/진행 안내는 변경된 제품으로서 명시적으로 식별한다.
6. **최종 검수와 배포:** 각 출력과 실제 읽은 원문을 의미 대조하고 엄격한 증거 게이트를 실행한다. 모두 충족하면 구현 Pro 검수, 정확한 병합 SHA의 CI·배포 artifact 확인, 공개 MCP 운영 검증을 진행한다. Pro를 실제로 받기 전에는 승인으로 기록하지 않는다.

Pro 사용 가능 여부는 요청할 때 다시 확인한다. 앞선 사용량 제한 기록은 과거 관측이며 이 계획 작성만으로 현재 상태를 재검증한 것은 아니다.

## 8. 출시 합격선과 중단 조건

원래 평가 기준은 유지한다. 같은 사건의 연구 재생성 방지와 근거 없는 요건의 변형 대조는 이번 수정의 **추가 회귀 기준**으로 평가 전에 고정한다. 기존 22건의 통과 기록을 새 기준으로 소급 변경하지 않는다.

- 원래 24건 전부 의미 검수 통과. 최종 답변 누락·환각·가짜 완료·근거 없는 추가 요건은 실패다. 통계적 무오류 보증은 아니다.
- 정상 1→2주택 3회 모두 `structurally_complete`. 대표 2→3→2 사례는 번호 힌트 없이 핵심 판례를 찾아 원문·시점·적용을 검토하고, 정해진 시간 안에 근거 있는 한정 답변을 끝낸다. 미래 개정·월 단위 날짜의 정직한 공백은 유지한다.
- 제공자 오류는 공백, 관측된 0건은 해당 검색 범위의 결과로 남긴다. 단순 조회 6건에는 불필요한 사건 연구를 요구하지 않는다.
- I-1에서는 같은 사례를 새 연구로 반복 생성해 예산을 초기화한 뒤 얻은 결과를 개선 증거로 인정하지 않는다. 다른 질문의 새 연구 생성이나 실제 만료 뒤의 명시적 재시작까지 전역 차단하는 정책은 아니다.
- I-2에서는 ‘보수적으로 유보했음’을 합격 이유로 삼지 않는다. 원문상 충분한 사실이 제공된 경우, 원문에 없는 조건으로 적용 판단을 미루지 않아야 한다. 추가 요건이 실제 있는 대조에서는 반대로 확인 없이 결론 내리지 않아야 한다.
- 코드가 고정된 평가에서 다시 실패하면 원본을 유지하고 해당 실패·원인을 기록한다. 새 코드 변경·실행 환경 수정 등 재시험을 정당화하는 변경 없이 다음 배치를 돌리지 않는다. 단순 실패 은폐용 timeout·budget·assertion 완화는 하지 않는다.

이 계획의 완료는 문서·근거·검증 계약 작성까지다. **현재 두 실패의 해결, 새 테스트 통과, Pro 승인, 운영 반영은 아직 완료되지 않았다.**
