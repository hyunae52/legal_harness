# MCP 자동 갱신 (2026-10-07)

사용자 요청에 따라 기존의 MCP 업데이트별 수동 승인 정책을 이 문서로 대체한다.
일반 교정·실패사례·법리 PR의 검수 정책은 별도다.

| 한국시간 | 실행 위치 | 처리 |
| --- | --- | --- |
| 매일 02:10 | 세법 포크 GitHub Actions | zisu17 원본을 검사하고 Python 3.11/3.13 테스트 후 포크 병합·릴리스 |
| 매일 02:40 | Legal Harness GitHub Actions | 공식 law npm 안정판과 포크 릴리스를 고정하고 통합 검사 후 main 반영 |
| Review 성공 후 | GitHub Actions → GCE | 검증된 artifact 설치, 실제 조회, 전환·복구 |
| 매일 03:30 | 기존 GCE cron | 운영 버전·변경 후보·동기화/갱신/배포 결과를 기존 이메일로 통지 |

GitHub 예약 실행은 지연될 수 있다. 앞 단계가 늦으면 다음 날 재시도하며, 36시간 이상
실행이 없거나 실패한 경우 메일에 표시한다. 새 릴리스가 없어도 main Review를 실행해
이전 배포 실패를 재시도한다. 실행 중인 버전이 일치하면 파일·의존성 검증 후 재시작 없이 끝난다.

세법은 원본의 고정 커밋을 포크에서 먼저 검증한다. 실행 내용 변경 시 동일 버전에서도
`.postN`을 올리고 태그는 덮어쓰지 않는다. 원본 비공개·조회 실패·라이선스 변경·로컬 패치
충돌·테스트 실패는 기존 배포본을 유지한다. 원본 main을 GCE에서 직접 pull하지 않는다.

서버 갱신 PR에는 law 버전, npm 잠금 파일, tax 고정 커밋·아카이브 SHA-256·도구 스키마만
들어간다. 후보 시험 job은 쓰기 권한과 운영 비밀이 없다. 별도 게시 job이 파일 범위와
메타데이터를 재검사하고 main이 그대로일 때만 검증 커밋을 fast-forward한다.
GITHUB_TOKEN push로 Review가 실행되지 않는 점을 고려해 main Review를 명시적으로 dispatch한다.
그 실행의 성공을 기다린 뒤 정확한 검수 실행 ID·시도 번호로 Deploy도 명시적으로 요청한다.
토큰으로 시작한 Review의 후속 workflow_run만으로 배포가 이어진다고 가정하지 않는다.

고정 GCE 배포기는 MCP 버전 변경만 허용하도록 설정한다. DB migration이나 배포기 변경은
계속 수동 운영 작업이다. 앱별 provider manifest/env 파일로 앱·law·tax를 함께 선택하며,
새 후보의 실제 법령·세법 본문 조회가 성공해야 기존 서비스 전환을 시작한다.
전환 후 실제 MCP 조회가 실패하면 이전 앱과 provider 선택을 복구한다. 복구조차 확인할 수
없는 장애에서는 공개 차단을 유지하며 배포 실패로 표시하므로 운영자 확인이 필요하다.
현재·직전 앱 및 tax provider를 보존하고 소유권이 확인된 과거 자동 설치본만 정리한다.

법률 판단의 정확성을 보장하는 검사가 아니라 조회·버전·설치·복구 검증이다.
미래의 새 버전에서 도구 삭제나 응답 계약 변경이 생기면 자동 갱신을 멈출 수 있다.

운영 토큰을 Actions/GCE에 새로 저장하지 않는다. Actions의 일회성 GITHUB_TOKEN,
기존 제한 SSH 배포키, 기존 SMTP 설정을 이용한다. 자동 PR 게시를 위해 두 저장소의
`Allow GitHub Actions to create and approve pull requests`를 활성화하되 자동 approve는 하지 않는다.

중지하려면 두 저장소의 자동 갱신 workflow를 Disable한다. 메일 cron은 별도로 유지할 수 있다.
수동 실행은 각 Actions 화면의 Run workflow, 반영 여부는 `/health`와 Deploy 실행 기록에서 확인한다.
