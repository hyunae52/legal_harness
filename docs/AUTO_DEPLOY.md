# main 자동 배포

사용자 요청: GitHub main에 반영한 변경을 검사 후 기존 GCE에 자동 배포한다. PR 생성·테스트는 배포 권한이 아니다. main 반영이 운영 앱 변경의 승인 지점이다.

## 동작 계약

1. 기존 Review 워크플로가 main push를 검사하고, 설치 시험을 통과한 바로 그 패키지를 배포 artifact로 보관한다.
2. 배포 워크플로는 같은 저장소의 main push에 대한 성공한 Review 실행만 받는다. PR·포크·실패·취소된 실행은 제외한다.
3. GCE는 실행 ID·attempt·저장소·브랜치·검사 단계·artifact digest를 GitHub API로 다시 확인한다. 현재 main과 다른 과거 실행은 배포하지 않는다.
4. 전용 SSH 키는 고정 수신기에만 접근한다. 임의 명령·PTY·포트 전달은 허용하지 않는다. 앱 운영 비밀은 기존 GCE 환경 파일에 남는다.
5. 배포는 GCE의 독립 systemd 작업으로 수행한다. Actions/SSH 연결이 끊겨도 활성화나 복구를 중간에 취소하지 않는다. 서버 잠금으로 동시에 하나만 실행한다.
6. 새 경로에 설치·검증한 다음 유입 차단 → 진행 중 요청 종료 대기 → 전환 → MCP 확인 → 유입 재개의 순서를 따른다. 검증 실패 시 이전 경로를 복구하고 확인한 뒤 재개한다. 복구 자체가 실패하면 자동 재개하지 않는다.
7. 패키지에는 없는 DB 변경·조회 엔진 버전 교체·배포기 자체 변경은 별도 운영 검증을 요구한다. 자동 배포기는 해당 fingerprint/버전 변경을 감지하면 기존 서비스를 유지하고 중단한다.
8. 자동 배포가 만든 경로만 보관 주기로 정리한다. 현재·직전 버전을 보존하며 기존 수동 배포 경로와 조회 엔진 설치본은 삭제하지 않는다.

## 사용 방법

앱 코드·규칙·안내 페이지 변경을 PR로 검토하고 main에 병합한다. GitHub Actions의 Review 다음 Deploy 실행에서 결과를 확인한다. 배포 실행은 활성화 도중 새 push 때문에 취소되지 않는다. 배포 직전 main이 바뀌었으면 이전 실행을 건너뛰고 새 검사를 기다린다.

별도 서버를 추가하지 않는다. 테스트와 빌드는 GitHub hosted runner에서 수행하고 GCE에는 검사한 패키지와 운영 의존성만 설치한다. 실패한 실행을 다시 수행할 때도 같은 커밋과 검사 결과를 다시 대조한다.

배포로 앱이 재시작되면 기존 메모리 연구 세션은 종료된다. 완료된 교정 PR과 영속 저장소는 이 과정에서 삭제하지 않는다.

## 운영 경로

- 고정 배포기: `/opt/legal-harness-deployer`
- 작업·보고서·자동 배포 설치본: `/home/cta/legal-harness-autodeploy`
- 앱 서비스: `legal-harness-a.service`
- GitHub 환경: `production` (main만 허용)

구현과 운영 검증 결과는 이 문서와 연결된 PR에 기록한다.
