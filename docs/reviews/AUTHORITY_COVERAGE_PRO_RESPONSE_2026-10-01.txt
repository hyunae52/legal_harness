1. 조회 의무를 만드는 입력과 검색 완료 인정 조건이 아직 실행 가능한 계약이 아닙니다

구체적 실패 경로:
모델이 중립 검색과 반대 검색에 사실상 같은 편향된 검색어를 사용하거나, 지나치게 좁은 검색 조건으로 0건을 받은 뒤 “보완 검색 완료”로 연결할 수 있습니다. 프로필이나 적용 법령 앵커가 아직 확정되지 않은 상태에서 어떤 자료군을 생성할지도 명확하지 않습니다. 자료군 이름과 성공 응답만 확인하는 구현이라면 “판례 검색 0회”가 “의미 없는 판례 검색 몇 회”로 바뀔 뿐입니다.

계획은 필터 지원 확인과 검색어 확장을 요구하지만, 어떤 관측 결과를 어떤 의무의 충족으로 인정할지는 아직 정하지 않았습니다.

필요한 계획 수정:
버전이 있는 조회 의무 명세와 검색 기록의 수락 판정표를 추가해야 합니다. 최소한 다음을 결정해야 합니다.

적용 법령·조문 앵커가 미확정일 때의 상태와 후속 의무 생성 시점.
일반 사건의 기본 의무, 세법 추가 의무, 프로필 미선택·미지원 시의 처리. 모델 선언 하나로 의무가 줄어들어서는 안 됩니다.
중립·반대·후속 검색별 필수 앵커, 질의 확장 규칙, 지원되는 필터, 페이지 종료 및 범위 미확인 조건.
복합 조회 도구의 일부 자료군만 성공했을 때의 처리. 하위 결과를 관측할 수 없다면 전체 자료군 완료로 세지 않아야 합니다.

무제한 전수 검색을 요구하라는 뜻은 아닙니다. 정책이 미리 정한 제한된 검색 범위의 완료와 남아 있는 검색 범위의 공백을 구분해야 합니다.

검증 예: 같은 검색을 중립·반대로 중복 제출, 조문 앵커 미확정, 지원되지 않는 법원 필터, 다음 페이지가 남은 응답, 복합 조회 중 법령만 성공한 응답을 각각 주입합니다. 이들이 판례 의무를 닫지 못하고, 실제로 규정된 보완 검색을 끝낸 정상 0건만 검색 수행 완료가 되어야 합니다.

2. “주요 후보”를 모델이 우회하지 못하도록 정하는 기준과 후보 신원·수명 계약이 필요합니다

근거 위치: 계획 §5.1–5.2 93–114줄, 후보 처리 필드 153–155줄, AC-11 196줄. 현재 src/researchEvidence.ts의 검색 결과 처리 분기는 검색 응답을 discovery_only passage로 보관하며, src/research.ts:81–91은 계획·사실 변경 시 증거 배열을 비웁니다.

구체적 실패 경로:
검색 응답에 불리한 상위 판례가 포함돼도 모델이 이를 “주요 후보가 아님”으로 분류하면, 원장을 남기는 것만으로 원문 검토를 강제할 수 없습니다. 또한 후보와 원문 receipt가 단순 참조로만 연결되면 후보 A를 처리했다고 하면서 다른 문서 B의 원문을 연결하는 오류를 별도로 막아야 합니다.

revision 변경도 중요합니다. 동일 쟁점을 유지한 채 사실 하나를 보완했는데 후보 원장까지 초기화된다면, 이미 발견한 불리한 후보가 다음 검색에서 재발견되지 않았다는 이유로 사라질 수 있습니다.

필요한 계획 수정:
검색 응답에서 서버가 추출한 후보 집합과 모델이 제출하는 적용·구별 판단을 분리해야 합니다. 후보 식별자는 원천·자료군의 이름공간과 문서 식별자를 포함하고, 원문 receipt의 문서 신원과 대조해야 합니다. 서로 다른 자료군의 같은 숫자 ID를 같은 문서로 합치면 안 됩니다.

원문 검토가 필수인 후보를 정하는 조건도 서버 관측 정보로 고정해야 합니다. 예를 들어 해당 조문 참조, 관측된 법원·심급, 인용 문서의 후속 사건 연결 등이 기준이 될 수 있습니다. 정보가 부족한 후보를 모델이 임의로 낮은 우선순위로 확정하는 경로는 두지 않아야 합니다.

revision 변경 시에는 후보 신원·발견 이력 보존과 현재 적용 판단의 무효화를 구분해야 합니다. 이전 후보를 자동 채택하라는 것이 아니라, 재검토 필요 또는 범위 변경으로 보관하되 조용히 삭제하지 말라는 뜻입니다.

검증 예: 불리한 후보를 non_major로 낮추기, 후보 A에 B의 receipt 연결하기, 서로 다른 원천의 동일 숫자 ID 충돌, 사실 보완 후 기존 후보 누락을 시험합니다. 반면 명백히 다른 문서임을 서버가 확인한 후보까지 모두 전체 원문 조회하도록 강요해서는 안 됩니다.

3. 정상 0건·대체 성공·revision을 모든 완료 검사에 적용하는 공통 판정표가 필요합니다

근거 위치: 계획 §4.2 77–87줄, §5.2 105–110줄, §7.2 160–162줄. 관련 현재 코드는 다음과 같습니다.

필요한 계획 수정:

검색 기록과 문서 증거를 구별하고, completed_no_candidate는 해당 검색 의무만 닫도록 해야 합니다. 후속 후보가 없는 경우에는 검증된 검색 ID로 수행을 입증할 수 있어야 하며, 없는 후속 문서 인용을 요구해서는 안 됩니다. 실제 후보가 있으면 원문·처리 의무는 그대로 남습니다.

실패 기록은 보존하되, 같은 의무·범위를 충족한 대체 성공과의 연결을 별도로 보관해야 합니다. 과거 revision의 시도는 감사 이력이지 현재 완료를 영구 차단하는 조건이 되어서는 안 됩니다. 반대로 과거 성공을 현재 의무에 자동 승계해서도 안 됩니다.

한도를 늘리는 대신 다음 실행 계약을 고정해야 합니다.

검색·후보 메타데이터와 인용 원문 저장을 분리하고 각각의 상한을 정해야 합니다. 큰 원문은 검증 가능한 요청 단위 또는 분할 조회로 확보하는 경로를 정하되, 단순히 잘린 본문을 완전하다고 승격해서는 안 됩니다. 대표 정상 사건에 대해 사실 보완·검색·후속 조회·원문 확보·재시도를 포함한 실제 호출 및 저장 예산표도 필요합니다.

재개는 세션·revision·의무·단계에 묶인 서버 작업 ID, 단계별 결과 저장, 진행 중 작업 소유권, 재전송 응답 규칙으로 정의해야 합니다. 응답을 잃은 완료 단계는 재조회하지 않고 기존 결과를 돌려주며, 만료·재시작 후에는 기존 메모리 계약상 이어갈 수 없음을 명확히 해야 합니다.

복합 제공자 도구의 내부 호출이 관측되지 않는다면 그 내부 호출 수까지 측정했다고 주장할 수 없습니다. 필수 조사에 필요한 하위 기록을 받거나 관측 가능한 원자 호출로 구성해야 합니다.

검증 예: receipt 한도를 넘는 필수 판결 원문, 많은 검색 후보, 조사 후 사실 한 번 보완, 단계 완료 직후 응답 유실, 살아 있는 작업 중 재전송, TTL 직전 재개를 시험합니다. 정상 사례에는 실제 완료 경로가 있어야 하고, 넘친 범위는 명시적으로 미완료여야 합니다. 쟁점 삭제나 조용한 조사 범위 축소로 예산을 맞춰서는 안 됩니다.

5. 24회 모델 파일럿에 측정 항목은 있지만 출시 합격·불합격 기준이 없습니다

근거 위치: 계획 §10 210–231줄, 단계별 독립 검수·배포 252–270줄, 완료 기준 274–284줄.

구체적 실패 경로:
현재 문구대로라면 24회에서 판례 발견이 대부분 실패하거나 모든 사건에 조건부 답변만 내더라도, 결과를 기록했다는 이유로 “실제 모델 행동 검증 완료”를 표시할 여지가 있습니다. 반대로 제보 모델을 정확히 확인할 수 없을 때 무엇을 대체 평가할지, 어느 범위의 출시 주장을 보류할지도 정해져 있지 않습니다.

필요한 계획 수정:
파일럿 실행 전에 다음 세 가지를 분리한 출시 판정표를 고정해야 합니다.

판단 대상	필요한 기준
서버 구조 안전성	F-01~03 우회, 미충족 검색의 완료 승격, 후보 신원 바꿔치기 등이 한 건이라도 재현되면 수정 필요
대표 사례의 실제 조사·정상 사용성	번호 힌트 없는 핵심 근거 발견과 원문 검토, 대응 정상 사례의 부당한 차단 여부에 사전 합격선을 설정
모델·클라이언트 행동	서버가 미완료라고 했는데 모델이 확정·검수 완료라고 발언한 실패를 별도 집계하고, 해당 조합의 지원·출시 주장에 반영

예를 들어 대표 실패·정상 대조 시나리오의 각 3회에서 필요한 동작을 모두 확인하는 것을 파일럿 통과선으로 정할 수 있습니다. 이는 제가 제안하는 운영상 합격선이지 통계적 정확도 보증이 아닙니다. 장애 시나리오는 기대된 조건부 처리와 정상 조사의 성공을 구별해야 하며, 장애 발생 건을 사후에 분모에서 빼서는 안 됩니다.

제보 모델을 확인할 수 없다면 식별 가능한 다른 모델·클라이언트로 평가 범위를 명시할 수 있지만, 그것을 원래 사건의 원인 규명이나 해당 모델의 개선 확인으로 대체하면 안 됩니다. 필수 평가가 미실행이면 “완료”가 아니라 미검증 또는 범위 제한 상태가 되어야 합니다.

검증 예: “모든 답변을 유보해서 우회는 0건”, “서버 게이트는 정상이나 모델이 미완료를 숨김”, “실제 검색은 실패하고 문서번호 직접 조회만 성공”, “정상 사례도 계속 차단”이라는 결과를 넣어 출시 판정표가 각각 어떤 결론을 내는지 확인합니다. 대표 입력의 월 단위 날짜 때문에 남는 사실 공백도 판례 검색 실패와 분리해서 평가해야 합니다.

(d) 이미 충분히 반영된 사항과 남는 한계

정상 0건에 가짜 반례를 요구하지 않는 원칙, 사건일 이후 판결을 일괄 배제하지 않는 원칙, 법령 개정·부칙과 사실 차이를 확인하는 원칙, 자기 인용이 입증하는 이력과 후속 검색 수행을 구분하는 원칙은 이미 계획에 있습니다. 이를 다시 추가하라는 지적은 아닙니다. 위 지적은 그 원칙을 서로 충돌하지 않는 실행 계약으로 고정하라는 요구입니다.

또한 제공자의 authorityLevel 하나나 예규 본문의 “대법원” 문구로 권위를 승격하지 않는 설계도 적절합니다. 추가 서버 LLM, 새 DB, 새로운 사용자 수 제한을 필수화할 이유는 없습니다.

수정 후에도 서버가 보장할 수 있는 것은 등록된 범위에서 정책상 필요한 검색이 실제 수행됐고, 관측된 후보와 출처 신원이 보존되며, 요구된 검토 연결이 제출됐다는 것까지입니다. 공식 원천의 인덱싱 누락, 등록하지 않은 쟁점, 형식은 갖췄지만 법적으로 틀린 구별 이유, MCP 밖에서 모델이 하는 발언까지 결정론적 검사로 해결했다고 주장해서는 안 됩니다.

최종적으로, 이 계획은 폐기하거나 전면 재설계할 대상은 아닙니다. 위 5개 계약을 계획에 명시한 뒤 구현 단계로 넘기는 것이 적절하며, 현 초안에 대한 무조건적인 PLAN PASS는 주지 않습니다.
